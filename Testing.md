# Testing

Как устроены хостовые тесты NATALIA Core, как добавить новый и какие тесты нужно
написать. Задачи в разделе 6 оформлены так, чтобы каждую можно было целиком
перенести в отдельный issue.

Уровень, который проверяется, описан в [`Algorithm.md`](Algorithm.md).
Аппаратный контракт и поведение заглушки — в [`Board_API.md`](Board_API.md).

---

## 1. Что это за тесты

Хостовые тесты собирают уровень `Algorithm` под обычный ПК, подставляя вместо
аппаратуры программную заглушку `Board_API`. Плата и кросс-компилятор не нужны.

Это основной способ регрессионной проверки: автомат состояний, действия, разбор
протокола CAN, работа с MRAM и контроль аварий проверяются целиком. Всё, что
требует настоящей периферии, ими не покрывается — для этого есть стендовые
программы в `tests/firmware/`.

Сейчас: **12 программ, 71 проверочная функция.**

### Запуск

```bash
cmake -S . -B cmake-build-tests -G Ninja \
  -DNATALIA_BUILD_TESTS=ON \
  -DNATALIA_USE_BOARD_STUBS=ON

cmake --build cmake-build-tests -j 18
ctest --test-dir cmake-build-tests --output-on-failure
```

Один тест отдельно:

```bash
ctest --test-dir cmake-build-tests -R test_erase --output-on-failure
```

Ожидаемый результат — `100% tests passed`. Любой упавший тест означает регрессию,
а не «так и было».

## 2. Как добавить новый тест

Четыре шага. Ничего, кроме них, делать не нужно.

### Шаг 1. Создать файл `tests/test_<имя>.c`

Тесты не используют внешний фреймворк. Проверка — обычный `assert()`, программа
возвращает `0` из `main()`. Падение `assert` роняет процесс, и `ctest` считает
тест провалившимся.

```c
#include <assert.h>
#include <stdbool.h>
#include <stdint.h>
#include <string.h>

#include "algorithm.h"
#include "board_api.h"
#include "board_comm_stub.h"
#include "board_stub.h"
#include "event_queue.h"
#include "mram_store.h"
#include "state.h"
#include "transport.h"

#define ADDR_NA  (0x1EU)
#define ADDR_BVS (0x05U)

static void begin_test(SystemContext *ctx, SystemState state) {
    memset(ctx, 0, sizeof(*ctx));
    ctx->state = state;
    ctx->previous_state = state;
    ctx->nand1.bank = NAND_BANK_1;
    ctx->nand2.bank = NAND_BANK_2;

    system_event_queue_init();
    board_comm_stub_reset();
    transport_reset();
}

static void my_first_case(void) {
    SystemContext ctx;

    begin_test(&ctx, STATE_DUTY);

    /* воздействие и проверки */
}

int main(void) {
    my_first_case();

    return 0;
}
```

`begin_test()` обязателен в начале **каждой** проверочной функции. Без
`transport_reset()` состояние очереди передачи протечёт из предыдущей функции и
проверки ответов начнут ловить чужие сообщения.

### Шаг 2. Зарегистрировать в `tests/CMakeLists.txt`

Скопировать блок, заменив имя. Порядок блоков в файле значения не имеет.

```cmake
add_executable(test_<имя>
        test_<имя>.c
)

target_link_libraries(test_<имя> PRIVATE
        natalia_algorithm
)

target_compile_options(test_<имя> PRIVATE
        -Wall
        -Wextra
        -Wpedantic
)

add_test(NAME test_<имя> COMMAND test_<имя>)
```

Первая строка `tests/CMakeLists.txt` — `add_compile_options(-UNDEBUG)`. Она
нужна, потому что проект собирается с `RelWithDebInfo`, а тот определяет
`NDEBUG` и превратил бы все `assert()` в пустое место. **Не удаляйте её**, иначе
тесты станут молча проходить всегда.

### Шаг 3. Вызвать новые функции из `main()`

Регистрация проверочных функций ручная: если функцию не вызвать из `main()`, она
просто не выполнится, и никакого предупреждения не будет.

### Шаг 4. Собрать и прогнать

```bash
cmake --build cmake-build-tests -j 18
ctest --test-dir cmake-build-tests -R test_<имя> --output-on-failure
```

Сборка должна быть без предупреждений: тесты собираются с `-Wall -Wextra -Wpedantic`.

## 3. Два способа подать воздействие

**Через протокол** — проверяется и разбор transport, и автомат. Так следует
писать всё, что связано с командами.

```c
uint8_t payload[6];
memset(payload, 0xAA, sizeof(payload));
payload[0] = 0x01U;                    /* содержимое команды */

board_comm_stub_inject_rx(0x0F08U, ADDR_BVS, ADDR_NA, payload, 6U);
transport_poll(&ctx, 0U);
algorithm_process_events(&ctx);
```

**Напрямую событием** — проверяется только автомат, разбор пропускается. Так
удобно проверять внутренние события и редкие ветви.

```c
SystemEvent event;
memset(&event, 0, sizeof(event));
event.type = EVENT_CMD_ERASE;
event.command.erase.bank = NAND_BANK_1;

assert(system_event_queue_push_back(&event));
algorithm_process_events(&ctx);
```

Длительные режимы прокручиваются циклом со счётчиком-предохранителем, чтобы тест
не завис, если режим не завершится:

```c
uint32_t guard;

for (guard = 0U; (guard < 1000U) && (ctx.state == STATE_ERASE); ++guard) {
    algorithm_poll(&ctx);
    algorithm_process_events(&ctx);
}
assert(ctx.state == STATE_DUTY);
```

Проверять результат можно по `SystemContext`, по содержимому MRAM через
`mram_store_*` и по последнему переданному сообщению через
`board_comm_stub_last_tx()`.

## 4. Ловушки

**Состояние заглушки не сбрасывается между проверочными функциями.**
`board_stub_init_once()` отрабатывает один раз за процесс, функции полного
сброса нет. Внутри одного бинарника содержимое NAND и MRAM переносится из
функции в функцию. Либо задавайте исходное состояние явно, либо снимайте
опорное значение в начале и сравнивайте приращение — как сделано в
`test_erase.c` (`save_erase_baseline`). Задача S-01 убирает эту ловушку.

**Слот приёма один.** Второй `board_comm_stub_inject_rx()` до вызова
`transport_poll()` затирает первый.

**Слот передачи тоже один.** `board_comm_stub_last_tx()` отдаёт только последнее
сообщение. Если команда порождает и квитанцию, и ТС «Статус», проверяйте их по
шагам, сверяясь с `board_comm_stub_tx_count()`, а не одним вызовом в конце.

**Часы не идут.** `board_rtc_get_time()` возвращает ровно то, что записали через
`board_stub_set_rtc_time()`. Сценарии с течением времени выстраиваются вручную;
`now_ms` в `transport_poll()` и `alarm_monitor_poll()` тоже передаёте вы сами.

## 6. Задачи

Каждый блок — готовое содержимое issue. Приоритеты: **P1** — закрывает код,
который сейчас не проверяется вообще; **P2** — расширяет частичное покрытие;
**P3** — ждёт незавершённой функциональности.

Задачи с префиксом **S** — доработки заглушки. Они разблокируют остальные, и их
разумно делать первыми.

---

### S-01 · Полный сброс состояния заглушки

**Приоритет:** P1 · **Файлы:** `Algorithm/src/board_api_stub.c`,
`Algorithm/include/board_stub.h` · **Блокеров нет**

**Зачем.** Сейчас состояние NAND и MRAM переносится между проверочными функциями
внутри одного бинарника, потому что `board_stub_init_once()` срабатывает один раз
за процесс. Из-за этого тесты зависят от порядка вызовов, а авторам приходится
обходить проблему вручную. Это фундамент для всех остальных задач.

**Что сделать.** Добавить `void board_stub_reset_all(void)`, приводящую модель к
исходному состоянию: NAND заполнен `0xFF`, счётчики пакетов и признаки заполнения
обнулены, питание банков выключено, MRAM обнулена, инжектируемые значения
(температуры, питание, часы, счётчики событий, признаки отказов) возвращены к
умолчаниям.

**Готово, когда:**

- [ ]  функция объявлена в `board_stub.h` и описана в `Board_API.md`;
- [ ]  вызов добавлен в `begin_test()` существующих тестов;
- [ ]  `save_erase_baseline` в `test_erase.c` упрощён или удалён за ненадобностью;
- [ ]  все 12 программ проходят.

**Готово, когда:**

- [ ]  сводка ограничений в `Board_API.md` обновлена.

### S-04 · Управление подтверждением питания банка NAND

**Приоритет:** P2 · **Файлы:** `Algorithm/src/board_api_stub.c`,
`Algorithm/include/board_stub.h` · **Блокеров нет**

**Зачем.** `board_nand_is_powered()` отражает флаг модели, который выставляет сам

**Что сделать.** Добавить `void board_stub_set_nand_powered(uint8_t bank_id, bool powered)`, значение которого перекрывает флаг модели до следующего сброса.

**Готово, когда:**

- [ ]  инжектор работает отдельно для каждого банка;
- [ ]  описано в `Board_API.md`.

### S-05 · Очередь передачи и отказ передачи в заглушке связи

**Приоритет:** P2 · **Файлы:** `Algorithm/src/board_api_stub.c`,
`Algorithm/include/board_comm_stub.h` · **Блокеров нет**

**Зачем.** `board_comm_send()` в заглушке всегда успешна и хранит только
последнее сообщение. Из-за этого не проверяются: логика повторов
(`TRANSPORT_TX_MAX_RETRIES` = 3), переполнение очереди передачи на 4 сообщения и
любые сценарии, где нужно увидеть несколько ответов подряд. Разблокирует T-08.

**Что сделать.** Заменить одиночный слот передачи кольцевым буфером не менее чем
на 8 сообщений с доступом по индексу, и добавить
`void board_comm_stub_set_send_fail(uint32_t fail_count)` — заставить указанное
число ближайших вызовов вернуть ошибку.

**Готово, когда:**

- [ ]  доступно чтение произвольного переданного сообщения по индексу;
- [ ]  `board_comm_stub_last_tx()` сохранён для совместимости;
- [ ]  существующие тесты не сломаны;
- [ ]  описано в `Board_API.md`.

### T-01 · Очередь событий

**Приоритет:** P1 · **Файл:** `tests/test_event_queue.c` (новый) · **Блокеров нет**

**Зачем.** Очередь событий — центральный механизм всего верхнего уровня, и на неё
**нет ни одного теста**. Через неё проходит каждая команда и каждое внутреннее
событие; ошибка здесь ломает прибор целиком и молча.

**Случаи:**

- [ ]  порядок FIFO: три события через `push_back` извлекаются в порядке
  постановки;
- [ ]  `push_front` кладёт событие перед уже стоящими и извлекается первым;
- [ ]  заполнение до `SYSTEM_EVENT_QUEUE_CAPACITY` (32) успешно, все 32 события
  извлекаются в правильном порядке;
- [ ]  33-я постановка возвращает `false`, увеличивает счётчик переполнений и
  **не портит** уже стоящие события;
- [ ]  `pop` на пустой очереди возвращает `false` и не трогает выходную структуру;
- [ ]  `system_event_queue_get_count()` верен после произвольной
  последовательности постановок и извлечений;
- [ ]  переход через границу буфера: многократное чередование постановки и
  извлечения (больше 32 циклов) не нарушает порядок;
- [ ]  `clear` обнуляет счётчик элементов, но **сохраняет** счётчик переполнений;
  `init` обнуляет и его;
- [ ]  `push_back_type` / `push_front_type` дают событие с нужным типом и
  обнулёнными остальными полями;
- [ ]  полезная нагрузка `command` переживает круг «постановка — извлечение»
  без искажений.

**Готово, когда:** все случаи проходят, программа зарегистрирована в
`tests/CMakeLists.txt`, `ctest` зелёный.

### T-02 · Режим ALARM: выходы

**Приоритет:** P1 · **Файл:** `tests/test_alarm_mode.c` (новый) · **Блокеров нет**

**Зачем.** Существующие тесты проверяют только **вход** в ALARM. Ни один тест не
проверяет **выход** из него, а это единственный способ вернуть прибор в работу
после аварии. Обработчик `handle_alarm_event` содержит три разные ветви выхода,
и ни одна не покрыта.

**Случаи:**

- [ ]  `CMD_RESET_ALARM` сбрасывает признаки, `masked_alarm` обнуляется, прибор
  переходит в DUTY и выдаёт ТС «Статус»;
- [ ]  `CMD_RESET_ALARM` при взведённом немаскируемом признаке: квитанция
  приходит, но прибор **остаётся** в ALARM;
- [ ]  `CMD_SET_CFG` с маской, закрывающей взведённый признак, выводит в DUTY;
- [ ]  `CMD_SET_CFG` с маской, не закрывающей признак, оставляет в ALARM;
- [ ]  `CMD_SET_CFG`, пытающийся снять маску с немаскируемого бита, не выводит из
  ALARM (маска принудительно дополняется);
- [ ]  `EVENT_MASKED_ALARM_CLEAR` при нулевом `masked_alarm` выводит в DUTY;
- [ ]  `EVENT_MASKED_ALARM_CLEAR` при ненулевом `masked_alarm` ничего не меняет;
- [ ]  `CMD_TELEM_REQ` в ALARM отвечает квитанцией и ТС «Телеметрия»;
- [ ]  `CMD_STATUS_REQ` и `CMD_VERSION_REQ` в ALARM отвечают;
- [ ]  при выходе в DUTY вызывается `action_mark_alarm_exit` (проверяется по
  состоянию контекста).

### T-03 · Режим DUTY: переходы и команды

**Приоритет:** P1 · **Файл:** `tests/test_duty.c` (новый) · **Блокеров нет**

**Зачем.** DUTY — состояние, в котором прибор проводит большую часть времени и из
которого запускаются все остальные режимы. Сейчас покрыт **один** переход
(`duty_start_erase_with_payload` в `test_state_machine.c`). Допустимость команд
проверена отдельно, но сами переходы и ответы — нет.

**Случаи:**

- [ ]  `CMD_ERASE` → ERASE с правильным банком из аппаратной конфигурации;
- [ ]  `CMD_TEST` → TEST с правильным банком;
- [ ]  `CMD_DUMP` → DUMP с правильным банком, интерфейсом и числом пакетов;
- [ ]  `CMD_OBSERVE_START` → OBSERVE;
- [ ]  `CMD_OBSERVE_START` на заполненном банке отклоняется квитанцией с кодом
  `ERR_CONTENT` (байт `0x05`, а не `0x07`) и **не** меняет режим;
- [ ]  `CMD_SET_TIME` (0F02h) применяет миллисекунды и секунды к часам;
- [ ]  `CMD_STATUS_REQ` → ТС 0D00h с верным байтом режима;
- [ ]  `CMD_TELEM_REQ` → ТС 0D02h длиной 109 байт;
- [ ]  `CMD_VERSION_REQ` → ТС FFE1h длиной 3 байта;
- [ ]  `CMD_TEST_RESULT` → ТС 0D03h длиной 6146 байт;
- [ ]  `CMD_DUTY` в DUTY подтверждается и не меняет режим;
- [ ]  `EVENT_MASKED_ALARM_SET` в DUTY переводит в ALARM с безопасной
  конфигурацией.

### T-04 · Заполнение банка ППЗУ

**Приоритет:** P2 · **Файл:** `tests/test_nand_full.c` (новый) или дополнение
`test_observe.c` · **Блокеров нет**

**Зачем.** `EVENT_NAND_FULL` не встречается **ни в одном** тесте. Это штатное
завершение научного сеанса при исчерпании памяти — сценарий, который на орбите
случится обязательно.

Важно: событие порождается и обрабатывается **только в режиме наблюдений**
(`algorithm.c` — при неудачной записи по заполнению, `state.c` — в
`handle_observe_event`). В остальных режимах его нет и быть не должно, поэтому
«проверка заполнения во всех режимах» — некорректная постановка.

**Случаи:**

- [ ]  `EVENT_NAND_FULL` в OBSERVE завершает сеанс и переводит в DUTY с ТС
  «Статус»;
- [ ]  признак заполнения банка сохраняется в служебных данных MRAM;
- [ ]  отказ завершения (`ACTION_ALARM`) уводит в ALARM, а не в DUTY;
- [ ]  байт «идентификатор переполнения ППЗУ» в ТС «Статус» отражает заполненный
  банк;
- [ ]  признак заполнения переживает перезагрузку: сохранён в MRAM и прочитан при
  загрузке;
- [ ]  `CMD_OBSERVE_START` на заполненном банке отклоняется кодом `ERR_CONTENT`
  (пересекается с T-03, достаточно проверить в одном месте).

### T-05 · Восстановление MRAM и авария

**Приоритет:** P2 · **Файл:** `tests/test_mram_recovery.c` (новый) ·
**Блокируется S-02**

**Зачем.** Единственный аварийный признак, который сейчас реально выставляется в
коде, — `ALARM_MRAM`, и путь его установки на хосте недостижим. Резервирование
конфигурации — базовый механизм живучести прибора, и он не проверен.

**Случаи:**

- [ ]  первая копия невалидна, вторая валидна: конфигурация читается из второй;
- [ ]  вторая копия невалидна: чтение из первой;
- [ ]  одна копия невалидна: `action_restore_mram_copy` восстанавливает её из
  исправной, после чего обе валидны и содержат одно и то же;
- [ ]  обе копии невалидны: выставляется `ALARM_MRAM`, `masked_alarm` ненулевой;
- [ ]  обе копии невалидны при загрузке: `EVENT_BOOT` приводит в ALARM, а не в
  DUTY;
- [ ]  заводской образ **не** записывается автоматически (защита от молчаливой
  подмены конфигурации — это осознанное решение, тест его фиксирует).

### T-06 · Режим TEST: тракт данных

**Приоритет:** P2 · **Файл:** `tests/test_mode_test.c` (дополнение) ·
**Блокеров нет**

**Зачем.** TEST — режим, которым проверяют научную память перед сеансом. До
недавнего времени банк в заглушке был меньше одного блока, и тракт данных на
хосте не выполнялся вообще. Ёмкость поднята до 256 пакетов (два полных блока), и
запись, чтение и сравнение теперь реально исполняются — около 770 шагов поллера
за прогон. Но проверяет их по-прежнему только косвенный признак «режим дошёл до
конца и `Nerr` пуст». Ни один тест не подтверждает, что сравнение вообще
способно **обнаружить** ошибку.

Ключевой случай здесь — третий: без него весь тракт может молча сравнивать буфер
сам с собой и всегда давать ноль ошибок.

**Случаи:**

- [ ]  `total_blocks` соответствует ёмкости банка (сейчас 2 блока);
- [ ]  на исправной памяти `Nerr` по всем пройденным блокам равен нулю;
- [ ]  внесённое искажение в банк даёт ненулевой `Nerr` именно в том блоке;
- [ ]  `Nerr` сохраняется в область MRAM выбранного банка и читается обратно;
- [ ]  счётчик тестов банка увеличивается на единицу;
- [ ]  финальное стирание выполняется, банк после теста пуст;
- [ ]  бит «питание после завершения» соблюдается в обоих значениях;
- [ ]  досрочное завершение по `CMD_DUTY` не увеличивает счётчик тестов;
- [ ]  авария в ходе теста уводит в ALARM.

### T-07 · Отказ подтверждения питания

**Приоритет:** P2 · **Файл:** `tests/test_alarm_monitor.c` (дополнение) ·
**Блокируется S-04**

**Зачем.** Аварийные признаки `ALARM_NAND_PS` и `ALARM_PED_PS` выставляются двумя
разными путями: циклом контроля (покрыт) и в момент включения питания, когда
подтверждения не пришло (не покрыт для NAND). Второй путь — это защита от подачи
питания на неисправный узел.

**Случаи:**

- [ ]  `prepare_single_nand_bank` при неподтверждённом питании банка выставляет
  `ALARM_NAND_PS` и возвращает `ACTION_ALARM`;
- [ ]  вызвавшая команда после этого приводит прибор в ALARM, а не просто выдаёт
  ошибку;
- [ ]  то же для `confirm_ped_powered` и `ALARM_PED_PS`;
- [ ]  признак немаскируемый: маска, снимающая бит 11, не мешает уходу в ALARM;
- [ ]  при подтверждённом питании авария не выставляется.

### T-08 · Транспорт: очередь передачи и повторы

**Приоритет:** P2 · **Файл:** `tests/test_transport_tx.c` (новый) ·
**Блокируется S-05**

**Зачем.** Логика повторов и очередь передачи на 4 сообщения не проверяются:
заглушка всегда принимает передачу с первого раза. При этом одна команда может
порождать два ответа подряд (квитанция и ТС «Статус»), и их взаимный порядок
сейчас никем не зафиксирован.

**Случаи:**

- [ ]  квитанция уходит **раньше** ТС «Статус» для команды, порождающей оба;
- [ ]  отказ передачи вызывает повтор, всего не более трёх попыток;
- [ ]  после исчерпания попыток сообщение отбрасывается, а очередь не заклинивает;
- [ ]  заполнение очереди передачи (4 сообщения) и её разбор в правильном порядке;
- [ ]  попытка поставить пятое сообщение обрабатывается без потери уже стоящих;
- [ ]  длинное ТС занимает буфер: вторая длинная передача при занятом буфере
  отклоняется предсказуемо;
- [ ]  после завершения длинной передачи буфер освобождается и следующая проходит.

### T-09 · Приборное время

**Приоритет:** P2 · **Файл:** `tests/test_time.c` (новый) · **Блокеров нет**

**Зачем.** Время — основа привязки всей научной информации. Сейчас проверяется
только разбор полей, но не то, что время действительно применяется к часам, и не
разделение двух источников.

**Случаи:**

- [ ]  `CMD_SET_TIME` (0F02h) применяет миллисекунды и секунды к часам через
  `board_rtc_set_time`;
- [ ]  `CMD_SET_TIME` от БВС (0401h) применяет время так же;
- [ ]  при взведённом бите 1 в `can_control` команда 0401h **отбрасывается без
  квитанции**, часы не меняются;
- [ ]  при сброшенном бите команда 0401h выполняется;
- [ ]  квитанция на 0401h уходит с идентификатором 0401h, а не 0F02h;
- [ ]  значение `milliseconds >= 1000` отвергается;
- [ ]  поле «начальное приборное время RTC» из `CMD_SET_CFG` сохраняется в MRAM,
  но **на часы не применяется** — фиксация осознанного решения.

### T-10 · Режим OBSERVE через автомат

**Приоритет:** P3 · **Файл:** `tests/test_observe.c` (дополнение) ·
**Ждёт завершения режима наблюдений**

**Зачем.** Сейчас `test_observe` вызывает функции `observe_*` напрямую, минуя
автомат. Это проверяет расписание форматов, но не проверяет, что режим вообще
правильно запускается, управляется и завершается через события.

Браться имеет смысл **после** того, как режим наблюдений будет доведён до
финального вида: сейчас научная часть отсутствует, тела формирования пакетов
пустые, и значительная часть проверок окажется бессмысленной.

**Случаи:**

- [ ]  `CMD_OBSERVE_START` из DUTY переводит в OBSERVE и разбирает параметры
  сеанса;
- [ ]  `CMD_OBSERVE_CTRL` в OBSERVE меняет конфигурацию на лету;
- [ ]  `EVENT_RTC_1HZ` продвигает расписание форматов через автомат;
- [ ]  `EVENT_PED_TRIGGER` обрабатывается только в OBSERVE;
- [ ]  `CMD_DUTY` завершает сеанс и возвращает в DUTY;
- [ ]  КТ принимаются в OBSERVE и игнорируются в остальных режимах (пересекается
  с `test_admissibility`);
- [ ]  авария уводит в ALARM с корректным завершением сеанса.

## 7. Что проверить нельзя и почему

Чтобы не тратить время на заведомо непокрываемое.

**Нет соответствующего кода:**

- формирование пакетов научной информации — тела `ni_packet.c` пустые;
- аварийные признаки: температура МК и блока детекторов, направление и статус
  ПЭД, неустранимый отказ NAND, VBUS и отказ USB — эти признаки нигде не
  выставляются;
- тайм-аут вывода по USB с переходом в аварию.

**Не позволяет заглушка** (снимается задачами S-0x):

- неверная CRC копий MRAM — S-02;
- отказ подтверждения питания банка NAND — S-04;
- повторы и очередь передачи — S-05.

**Принципиально не проверяется на хосте:**

- защита очереди событий от одновременного доступа: критические секции
  собираются только под ARM, на хосте на их месте пустые функции. Корректность
  подтверждается только на плате;
- всё, что зависит от реального времени, реальных прерываний и настоящей
  периферии — для этого стендовые программы в `tests/firmware/`.

## 8. Рекомендуемый порядок

1. **S-01** — полный сброс заглушки. Делает все последующие тесты независимыми
   от порядка выполнения; без него новые тесты будут наследовать существующую
   ловушку.
2. **T-01, T-02, T-03** — три области, не покрытые вообще: очередь событий,
   выходы из аварии, переходы дежурного режима. Наибольшая отдача на единицу
   усилий.
3. **S-02 → T-05** — живучесть конфигурации.
4. **T-06** — тракт данных режима TEST. Блокер снят, задача берётся сразу.
5. **T-04, T-09** — заполнение памяти и приборное время.
6. **S-04 → T-07**, **S-05 → T-08** — оставшиеся пути отказов.
7. **T-10** — после доведения режима наблюдений.

Задачи T-01…T-03 независимы друг от друга и от S-01, поэтому их можно раздать
параллельно; S-01 стоит первым только потому, что упрощает всё остальное.
