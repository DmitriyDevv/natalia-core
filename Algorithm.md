# Algorithm

Описание уровня `Algorithm` — верхнего уровня прошивки NATALIA Core, который
реализует автомат состояний прибора, режимы работы, разбор протокола CAN и
хранение конфигурации. Здесь же описана хостовая заглушка `board_api_stub`,
через которую этот уровень тестируется без платы.

Аппаратный контракт описан отдельно: [`Board_API.md`](Board_API.md).
Сборка, флаги и общий обзор проекта — в [`README.md`](README.md).
Как писать тесты на этот уровень и что ещё не покрыто — в
[`Testing.md`](Testing.md).

Документ описывает **текущее состояние кода**. Незавершённые места отмечены
явно; там, где поведение запланировано, но не реализовано, это сказано.

---

## 1. Место уровня в проекте

```text
main.c / tests/            <- вызывают Algorithm
    Algorithm              <- этот документ
        Board_API          <- единственный аппаратный контракт
            BSP / Drivers
                регистры
```

`Algorithm` не обращается к регистрам, GPIO, шинам, DMA и обработчикам
прерываний. Любой доступ к аппаратуре — только через `board_api.h`.

Обратное тоже верно: `BSP` и `Drivers` ничего не знают про `SystemContext`,
`SystemEvent`, `SystemState` и `handle_event()`.

## 3. Модель исполнения

Главный цикл — один на все режимы, без логики режимов внутри. `main.c`:

```c
while (1) {
    now_ms = timebase_millis();

    watchdog_kick();                     /* сброс сторожевого таймера             */

    transport_poll(&ctx, now_ms);        /* принять сообщения -> положить события  */
    algorithm_collect_hw_events(&ctx);   /* тики RTC и триггеры ПЭД -> события     */
    alarm_monitor_poll(&ctx, now_ms);    /* цикл контроля параметров, раз в 20 с   */
    algorithm_poll(&ctx);                /* продвинуть длительную операцию на шаг  */
    algorithm_process_events(&ctx);      /* разобрать очередь -> handle_event()    */
}
```

Каждая из пяти функций делает ограниченную работу и возвращает управление.
Блокирующих ожиданий на уровне `Algorithm` нет.

Порядок важен: аппаратные события собираются **до** разбора очереди, поэтому
секундный тик, пришедший в этой итерации, обрабатывается в ней же.

Последовательность запуска:

```text
clock_init -> timebase_init -> debug_log_init
    -> init_system_context (state = INIT, alarm_mask = ALARM_ALL_MASK)
    -> system_event_queue_init
    -> EVENT_BOOT       (action_init_hardware -> check/restore/load MRAM)
    -> board_comm_init
    -> EVENT_INIT_DONE  (-> DUTY или ALARM)
    -> главный цикл
```

### `algorithm_poll()`

Продвигает поллер активного режима — и только его:


| Состояние | Поллер        |
| ------------------ | ------------------- |
| `STATE_ERASE`      | `erase_mode_poll`   |
| `STATE_TEST`       | `test_mode_poll`    |
| `STATE_OBSERVE`    | `observe_mode_poll` |
| `STATE_DUMP`       | `dump_mode_poll`    |

В `DUTY`, `INIT`, `ALARM`, `SHUTDOWN` не делает ничего.

Поллеры **не вызывают** `handle_event()`. Обнаружив завершение или отказ, они
кладут событие в очередь (`EVENT_ERASE_DONE`, `EVENT_TEST_DONE`,
`EVENT_DUMP_DONE`, `EVENT_NAND_FULL`).

### `algorithm_collect_hw_events()`

Переносит счётчики, накопленные обработчиками прерываний, в очередь событий.
Это единственный мост между прерываниями и автоматом:

```c
if (board_rtc_take_1hz_events(&count) == BOARD_OK) {
    while (count > 0U) { push_back_type(EVENT_RTC_1HZ); --count; }
}

```

Функции `board_*_take_*` работают на осушение: возвращают накопленное число и
обнуляют счётчик. Секундные тики собираются во всех режимах. События ПЭД в
очередь не попадают: при 100 кГц она переполнилась бы за миллисекунды. OBSERVE
забирает записи ПЭД (события и отметки секунд) из кольца пачками в своём поллере
(раздел 12).

### `algorithm_process_events()`

Единственное место, откуда вызывается `handle_event()`. За один вызов
разбирает не более `ALGORITHM_EVENTS_PER_POLL` событий (по умолчанию **8**,
`algorithm.c:15`), затем возвращает управление — очередь не может занять цикл
целиком.

## 4. Очередь событий

`Algorithm/src/event_queue.c`. Кольцевой буфер, статическая память, без
`malloc`. Ёмкость — `SYSTEM_EVENT_QUEUE_CAPACITY`, по умолчанию **32**
элемента типа `SystemEvent`.

```c
void     system_event_queue_init(void);
void     system_event_queue_clear(void);
bool     system_event_queue_push_back(const SystemEvent* event);
bool     system_event_queue_push_front(const SystemEvent* event);
bool     system_event_queue_push_back_type(EventType type);
bool     system_event_queue_push_front_type(EventType type);
bool     system_event_queue_post_type(EventType type);
bool     system_event_queue_pop(SystemEvent* event);
uint32_t system_event_queue_get_count(void);
uint32_t system_event_queue_get_overflow_count(void);
uint32_t system_event_queue_get_pending_types(void);
```

Переполнение не затирает данные: `push_*` возвращает `false` и увеличивает
счётчик, читаемый через `system_event_queue_get_overflow_count()`.

Однократные события, потеря которых повесила бы режим (`EVENT_ERASE_DONE`,
`EVENT_TEST_DONE`, `EVENT_DUMP_DONE`, `EVENT_NAND_FULL`, `EVENT_OBSERVE_DONE`) или
не увела бы в ALARM (`EVENT_MASKED_ALARM_SET`, ставится только на фронте),
кладутся через `system_event_queue_post_type`. При полной очереди тип события
запоминается в маске (по биту на каждый из 28 типов), и `pop`, освободив место,
ставит его в конец очереди — после событий, которые уже ждали. `clear` маску
сбрасывает.

Очередь рассчитана на то, что события в неё могут класть и главный цикл, и
обработчик прерывания. Поэтому каждая операция `push_*` и `pop` на время работы
с указателями буфера запрещает прерывания: сохраняет регистр `PRIMASK`,
выполняет `cpsid i`, меняет указатели и восстанавливает прежнее состояние через
`cpsie i`. Участок короткий — несколько присваиваний, — так что задержка
обработки прерываний пренебрежимо мала.

Этот код собирается только под ARM (`#if defined(__arm__)`). В хостовой сборке
на его месте оказываются пустые функции, потому что прерываний там нет. Из
этого следует практическое ограничение: хостовые тесты проверяют логику
очереди, но не могут проверить её защиту от одновременного доступа —
корректность этой защиты подтверждается только на плате.

`push_front` в рабочем коде не используется покa — приоритетная
постановка предусмотрена (в основном для аварий), но пока не задействована.

## 5. События

`EventType` (`state.h:27`) — 28 значений. Кто порождает каждое:


| Событие                                              | Источник                      | Состояние                                                                            |
| ----------------------------------------------------------- | ------------------------------------- | --------------------------------------------------------------------------------------------- |
| `EVENT_CMD_TELEM_REQ`, `EVENT_CMD_STATUS_REQ`, `EVENT_CMD_SET_TIME`         | `transport_handle_known_command`     | работает                                                                              |
| `EVENT_CMD_OBSERVE_START`, `EVENT_CMD_OBSERVE_CTRL`, `EVENT_CMD_DUTY`       | `transport_handle_known_command`     | работает                                                                              |
| `EVENT_CMD_DUMP`, `EVENT_CMD_SET_CFG`, `EVENT_CMD_ERASE`                    | `transport_handle_known_command`     | работает                                                                              |
| `EVENT_CMD_TEST`, `EVENT_CMD_TEST_RESULT`, `EVENT_CMD_SHUTDOWN`, `EVENT_CMD_RESET_ALARM` | `transport_handle_known_command` | работает                                                                              |
| `EVENT_CMD_VERSION_REQ`                                     | `transport_handle_known_command`     | работает                                                                              |
| `EVENT_TLM_TIME_SYNC`, `EVENT_TLM_MCILWAIN`, `EVENT_TLM_MAGFIELD`            | `transport_handle_known_telemetry`   | работает                                                                              |
| `EVENT_BOOT`, `EVENT_INIT_DONE`                             | `main.c` (`pump_internal_event`)     | работает                                                                              |
| `EVENT_ERASE_DONE`                                          | `finish_erase_step` (`algorithm.c`)  | работает                                                                              |
| `EVENT_TEST_DONE`                                           | `finish_test_step` (`algorithm.c`)   | работает                                                                              |
| `EVENT_DUMP_DONE`                                           | `finish_dump_step` (`algorithm.c`)   | работает                                                                              |
| `EVENT_NAND_FULL`                                           | `observe_report_end` (`observe.c`)   | работает                                                                              |
| `EVENT_RTC_1HZ`                                             | `algorithm_collect_hw_events`        | работает — сбор в главном цикле                                     |
| `EVENT_OBSERVE_DONE`                                        | `observe.c`                           | работает — конец сеанса (после КУ 6 / «Выключение») или сбой записи |
| `EVENT_MASKED_ALARM_SET`                                    | `alarm_raise` (`alarm_monitor.c`)    | работает — все 16 признаков, см. раздел 11                   |
| `EVENT_INIT_FAIL`                                           | `main.c` (`pump_internal_event`)     | при отказе`board_comm_init`                                                 |
| `EVENT_MASKED_ALARM_CLEAR`                                  | —                                    | **не порождается**: признаки аварий по документу сами не сбрасываются |

`EVENT_MASKED_ALARM_CLEAR` — не пробел, а следствие спецификации: аварийные
признаки «устанавливаются в месте обнаружения и автоматически не обнуляются».
Сбрасывает их только КУ «Сброс аварийного статуса» или смена маски по КУ
«Задание настроек», и обе обрабатываются в режиме `ALARM` напрямую, без события.
Обработчик события тем не менее есть во всех режимах.

### `SystemEvent`

```c
typedef struct {
    EventType      type;
    uint32_t       msg_id;      /* исходный MSG_ID для ответа ACK      */
    uint8_t        tlm_slot;    /* слот tlm_staging для КТ             */
    CommandPayload command;     /* union разобранных параметров команды */
} SystemEvent;
```

`CommandPayload` — union из девяти структур (`CmdErase`, `CmdTest`, `CmdDump`,
`CmdObserveStart`, `CmdObserveCtrl`, `CmdDuty`, `CmdSetTime`, `CmdSetConfig`,
`CmdTestResult`). Событие самодостаточно: после постановки в очередь исходное
сообщение CAN больше не нужно.

Полезная нагрузка КТ в событие не копируется — она кладётся в кольцевой буфер
`tlm_staging` (6 слотов по 128 байт), а в событии остаётся номер слота.

## 6. Автомат состояний

`Algorithm/src/state.c`. Восемь состояний:

```text
INIT -> DUTY -> { ERASE, TEST, OBSERVE, DUMP } -> DUTY
  |       |            |                            |
  +-------+------------+----------------------------+--> ALARM --> DUTY
          |                                         |
          +-----------------------------------------+--> SHUTDOWN
```

`handle_event()` обрабатывает **ровно одно** событие и устроен как диспетчер по
текущему состоянию:

```c
switch (ctx->state) {
case STATE_INIT:     return handle_init_event(ctx, event);
case STATE_DUTY:     return handle_duty_event(ctx, event);
case STATE_ERASE:    return handle_erase_event(ctx, event);
case STATE_TEST:     return handle_test_event(ctx, event);
case STATE_OBSERVE:  return handle_observe_event(ctx, event);
case STATE_DUMP:     return handle_dump_event(ctx, event);
case STATE_ALARM:    return handle_alarm_event(ctx, event);
case STATE_SHUTDOWN: return handle_shutdown_event(ctx, event);
}
```

Каждый обработчик — `switch` по `event->type`, где ветви пронумерованы в
комментариях номерами строк из «Таблицы состояний и переходов».

Общие помощники:


| Функция              | Назначение                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------ |
| `transition_to`             | Смена состояния с сохранением`previous_state`.                               |
| `reject_command`            | Команда недопустима в режиме — ACK с кодом`ERR_MODE` (0x07).           |
| `enter_alarm`               | `action_mark_alarm` -> `action_enter_safe_config` -> переход в `ALARM` -> ТС статуса. |
| `is_alarm_active`           | `ctx->masked_alarm != 0`.                                                                              |
| `finish_command_transition` | ACK + переход + ТС статуса, либо ACK с ошибкой.                            |
| `finish_command_result`     | ACK без перехода.                                                                           |
| `ack_status_from_result`    | `ActionResult` -> код ACK.                                                                          |

### Коды квитанции

Протокол определяет ровно пять кодов. Первый байт ТС «Квитанция» устроен так:
бит 0 — признак отклонения команды (`0` — принята, `1` — отклонена), биты 1–7 —
номер ошибки. Отсюда и получаются «неровные» значения байта:

| Номер ошибки | Обозначение | Байт квитанции | Кто выставляет |
| ---: | --- | --- | --- |
| 0 | `OK` | `0x00` | `ACTION_OK` |
| 1 | `ERR_MSG_ID` | `0x03` | transport — неизвестный `MSG_ID`, событие не создаётся |
| 2 | `ERR_CONTENT` | `0x05` | `ACTION_ERR_CONTENT` |
| 3 | `ERR_MODE` | `0x07` | `reject_command()` — команда недопустима в текущем режиме |
| 4 | `ERR_OTHER` | `0x09` | `ACTION_ERR_OTHER` и `ACTION_ALARM` |

Из четырёх значений `ActionResult` автомат получает только три разных кода —
`ACTION_ALARM` и `ACTION_ERR_OTHER` дают один и тот же байт `0x09`. Это не
недосмотр: отдельного кода «авария» в протоколе нет, а `ERR_OTHER` описан как
«иная ошибка», так что более точного варианта не существует.

Различаются эти два результата не квитанцией, а тем, что происходит после неё:

```c
case ACTION_ALARM:
case ACTION_ERR_OTHER:
default:
    return TRANSPORT_ACK_ERR_OTHER;   /* код один и тот же */
```

```c
(void)action_send_ack_status(event, ack_status_from_result(result));
if (result == ACTION_ALARM) {
    enter_alarm(ctx);                 /* только для ACTION_ALARM */
}
```

То есть `ACTION_ERR_OTHER` — «команду выполнить не удалось, прибор продолжает
работать в прежнем режиме», а `ACTION_ALARM` — «команду выполнить не удалось, и
это авария»: дополнительно выполняются `action_mark_alarm`,
`action_enter_safe_config`, переход в `ALARM` и выдача ТС «Статус». Наземный
сегмент отличает эти случаи по следующему за квитанцией ТС «Статус», а не по
коду квитанции.

Коды `ERR_MSG_ID` и `ERR_MODE` через `ActionResult` не проходят вовсе: первый
выставляет transport ещё до создания события, второй — `reject_command()` в
автомате, когда команда не разрешена в текущем режиме.

## 7. `SystemContext`

Единственное состояние уровня. Передаётся указателем во все функции; глобальных
переменных режима нет.

```c
typedef struct {
    SystemState      state;
    SystemState      previous_state;
    uint32_t         alarm_status;      /* признаки аварий, alarm.h        */
    uint32_t         alarm_mask;        /* маска из конфигурации           */
    uint32_t         masked_alarm;      /* alarm_status & alarm_mask       */
    uint16_t         observe_session_id;
    uint16_t         can_control;

    int16_t          pu_temp_min,  pu_temp_max;      /* пороги контроля,    */
    int16_t          ped_temp_min, ped_temp_max;     /* копия из MRAM       */
    uint16_t         pu_voltage_min,  pu_voltage_max;
    uint16_t         pu_current_min,  pu_current_max;
    uint16_t         ped_voltage_min, ped_voltage_max;
    uint16_t         ped_current_min, ped_current_max;
    bool             thresholds_loaded;              /* пороги из MRAM / КУ 8 */
    uint32_t         alarm_monitor_last_ms;          /* отметка цикла 20 с  */

    NandRuntimeState nand1, nand2;      /* питание/подключение/заполненность */
    PedRuntimeState  ped;
    UsbRuntimeState  usb;
    EraseContext     erase;             /* контексты режимов             */
    TestContext      test;
    DumpContext      dump;
    ObserveContext   observe;
    ShutdownContext  shutdown;
} SystemContext;
```

Пороги контроля дублируются из MRAM в контекст при загрузке
(`action_load_mram`) и при КУ «Задание настроек» (`action_apply_config`), чтобы
цикл контроля читал ОЗУ и не обращался к MRAM на каждой итерации.

У каждого длительного режима — свой контекст с полем `stage` (`EraseStage`,
`TestStage`, `DumpStage`, `ObserveStage`, `ShutdownStage`). Поллер продвигает
`stage`, автомат смотрит на него при завершении.

Контекст крупный: `TestContext` содержит `nerr[2048]` плюс два буфера по
2048 байт, `DumpContext` и `ObserveContext` — по буферу пакета 2048 байт.
`SystemContext` в тестах объявляют как локальную переменную — на хосте это
нормально, но при добавлении полей стоит помнить о размере стека.

## 8. Действия (`actions.c`)

49 функций `action_*`, все возвращают `ActionResult`. Автомат решает
**что** делать, действия — **как**. По группам:


| Группа                        | Функции                                                                                                                                                                                  |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Запуск и MRAM                | `action_init_hardware`, `action_load_mram`, `action_check_mram`, `action_restore_mram_copy`, `action_mark_init_done`, `action_mark_init_fail`                                                   |
| Аварии                        | `action_mark_alarm`, `action_enter_safe_config`, `action_recalc_masked_alarm`, `action_clear_alarm_status`, `action_mark_alarm_exit`                                                            |
| Ответы                        | `action_send_status`, `action_send_ack`, `action_send_ack_status`, `action_send_dump_ack`, `action_send_telem`, `action_send_test_result`, `action_send_version`                                |
| Конфигурация            | `action_set_time`, `action_apply_config`, `action_write_mram`                                                                                                                                   |

## 9. Transport

`Algorithm/src/transport.c` — граница протокола. Разбирает КУ/КТ, строит
`SystemEvent`, кладёт их в очередь и отправляет ТС. Переходов режимов не
содержит и `handle_event()` не вызывает.

Идентификаторы соответствуют редакции протокола **v2.1**.

### Команды управления (КУ)

Всего распознаётся 17 идентификаторов, а типов событий 14 — расхождение
объясняется под таблицей.


| MSG_ID   | Команда                                              | Событие                                                   |
| -------- | ----------------------------------------------------------- | ---------------------------------------------------------------- |
| `0x0F00` | Запрос телеметрии                           | `EVENT_CMD_TELEM_REQ`                                            |
| `0x0F01` | Запрос статуса                                 | `EVENT_CMD_STATUS_REQ`                                           |
| `0x0F02` | Предустановка времени                   | `EVENT_CMD_SET_TIME`                                             |
| `0x0F03` | Включение режима наблюдений      | `EVENT_CMD_OBSERVE_START`                                        |
| `0x0F04` | Управление режимом наблюдений | `EVENT_CMD_OBSERVE_CTRL`                                         |
| `0x0F05` | Дежурный режим                                 | `EVENT_CMD_DUTY`                                                 |
| `0x0F06` | Вывод данных                                     | `EVENT_CMD_DUMP`                                                 |
| `0x0F07` | Задание настроек                             | `EVENT_CMD_SET_CFG`                                              |
| `0x0F08` | Стирание ППЗУ                                   | `EVENT_CMD_ERASE`                                                |
| `0x0F09` | Тест ППЗУ                                           | `EVENT_CMD_TEST`                                                 |
| `0x0F0A` | Запрос результатов теста ППЗУ  | `EVENT_CMD_TEST_RESULT`                                          |
| `0x0F0B` | Выключение                                        | `EVENT_CMD_SHUTDOWN`                                             |
| `0x0F0C` | Сброс аварийного статуса              | `EVENT_CMD_RESET_ALARM`                                          |
| `0xFFE0` | Запрос версии ПО                             | `EVENT_CMD_VERSION_REQ`                                          |
| `0x0401` | Предустановка времени от БВС     | `EVENT_CMD_SET_TIME` — то же событие, что и`0x0F02`        |
| `0x0A61` | Установка Destination ID                    | обрабатывается в transport, события нет |
| `0x0A62` | Установка Device ID                           | обрабатывается в transport, события нет |

`0x0401` отличается от `0x0F02` только раскладкой полей и источником: автомату
безразлично, откуда пришло время, поэтому оба дают одно событие. Исходный
`MSG_ID` сохраняется в `event->msg_id`, чтобы квитанция ушла с тем
идентификатором, который прислали. Если в `can_control` взведён бит 1, `0x0401`
отбрасывается ещё до создания события — без квитанции.

`0x0A61` / `0x0A62` перехватываются в `transport_handle_known_command` до сборки
события: они меняют адреса самого транспортного уровня, автомата не касаются и
получают квитанцию напрямую. Следствие: проверки допустимости по режимам к ним
не применяется, они работают во всех семи режимах — что и требует протокол.

Длина данных каждой КУ должна точно совпадать с таблицей протокола v2.1:
0 байт — `0x0F00`, `0x0F01`, `0x0F0B`, `0x0F0C`, `0xFFE0`; 1 байт — `0x0F05`,
`0x0F08`, `0x0F09`, `0x0F0A`; 2 байта — `0x0A61`, `0x0A62`; 4 байта — `0x0F06`;
5 байт — `0x0F03`, `0x0F04`, `0x0401`; 6 байт — `0x0F02`; 68 байт — `0x0F07`.
КУ другой длины, в том числе дополненная байтами `AAh` до 6 байт (так было
в v2), получает квитанцию `ERR_CONTENT` (`05h`).

### Команды телеметрии (КТ)


| MSG_ID   | Содержание                                    | Длина | Событие        |
| -------- | ------------------------------------------------------- | ---------: | --------------------- |
| `0xF210` | Время, орбита, ориентация          |        125 | `EVENT_TLM_TIME_SYNC` |
| `0xF221` | Геомагнитное поле, ориентация |         76 | `EVENT_TLM_MAGFIELD`  |
| `0x0E00` | Параметры Мак-Илвайна                |         24 | `EVENT_TLM_MCILWAIN`  |

КТ ставятся в очередь независимо от режима, но обрабатываются только в
`OBSERVE`; остальные режимы их молча отбрасывают.

### Телеметрические сообщения (ТС)


| MSG_ID   | Сообщение                             | Состояние                                                                            |
| -------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `0x0D00` | Статус, 6 байт                     | работает                                                                              |
| `0x0D01` | Квитанция (ACK), 6 байт        | работает                                                                              |
| `0x0D02` | Телеметрия, 109 байт             | работает; байты 6–7 и 30–35 всегда нулевые, см. ниже        |
| `0x0D03` | Результаты теста, 6146 байт | работает                                                              |
| `0xFFE1` | Версия ПО, 3 байта                | работает; значения — заглушки`255/255/255`                        |

В ТС «Телеметрия» два блока полей заполнить нечем:

- байты 6–7 «Температура микроконтроллера ПУ» — Board_API отдаёт один
  аналоговый канал температуры без разделения на МК и блок детекторов, этот
  канал отдан под байты 12–13;
- байты 30–35 (статус ПЭД, конфигурация триггера, настройки наблюдений) — по
  протоколу нулевые вне режима наблюдений, а сам режим не завершён.

Версия ПО берётся из `Algorithm/include/unican_version.h` — одного заголовка на
ТС `0xFFE1` и на байты 106–108 телеметрии. Значения нужно заменить на реальные
номера выпуска.

### Передача

Кольцевая очередь на `TRANSPORT_TX_QUEUE_LENGTH` = 8 сообщений. Сообщения до
109 байт (квитанции, «Статус», «Версия», «Телеметрия» `0x0D02`) хранятся прямо
в ячейке очереди, поэтому несколько запросов телеметрии подряд получают каждый
свой ТС. Отдельный буфер `transport_long_tx_buffer` на 6146 байт — только для
«Результата теста» `0x0D03` (одно сообщение одновременно, флаг
`transport_long_tx_busy`; вторая КУ при занятом буфере получает квитанцию
«другое»). До `TRANSPORT_TX_MAX_RETRIES` = 3 повторов после первой попытки,
затем сообщение отбрасывается и очередь идёт дальше.

### Адресация

Адрес прибора по умолчанию `0x1E` (НА), получателя — `0x05` (БВ-С). Слово
`can_control` из конфигурации:


| Бит | Значение                                                                                            |
| ------ | ----------------------------------------------------------------------------------------------------------- |
| 0      | Отвечать отправителю запроса, а не по сохранённому адресу. |
| 1      | Игнорировать КУ предустановки времени`0x0401` от БВС.               |

Адреса, заданные командами `0x0A61` / `0x0A62`, разбираются как 16-битные
значения. Допустимы `0001h`…`3FFFh`: в 29-битном идентификаторе UniCAN под адрес
отведено 14 бит; `0000h` и значения больше `3FFFh` получают квитанцию
`ERR_CONTENT`, адрес не меняется. Принятый адрес сохраняется в MRAM (`mram_store_save_addresses` — чтение, правка,
запись, чтобы не затереть остальную конфигурацию). Исключение — режим
`SHUTDOWN`: там адрес меняется только в ОЗУ, как требует протокол. При загрузке
`action_load_mram` применяет сохранённые адреса через
`transport_apply_stored_addresses`; нулевое значение означает «никогда не
задавался», и тогда, как и для значения больше `3FFFh`, остаются значения по
умолчанию.

Принимаются только сообщения, адресованные текущему Device ID (до первой
смены — `0x1E`). Аппаратный фильтр CAN принимает все кадры, адрес проверяет
`transport_message_is_for_this_node`.

Кадр ТС «Телеметрия» берёт измерения через `transport_read_measurements(ctx, …)`;
датчики ПЭД (TMP112 0x49, INA219 0x41) опрашиваются только при включённой ПЭД,
иначе поля ПЭД нулевые.

## 10. Хранение в MRAM

`Algorithm/src/mram_store.c`. Две резервируемые копии, запись всегда в
обе (`write_both_copies`), чтение — из первой валидной.

Внутри копии (смещения задаёт `mram_store.c`, копия — 1024 байта):


| Смещение | Область                                                                                                                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0x0000`         | `MramStoreConfig` — пороги аварий, маска, `can_control`, параметры поясов, начальное время RTC, версия конфигурации, Destination ID и Device ID.                     |
| `0x0100`         | `MramStoreServiceData` — статус аварий, признаки заполнения банков, счётчики пакетов/стираний/тестов, последний выведенный пакет. |

Поля, добавленные редакцией v2.1 (`init_rtc_time_ms`, `destination_id`,
`device_id`), дописаны **в конец** `MramStoreConfig`. Структура пишется в MRAM
как есть, поэтому дописывание в конец сохраняет смещения всех прежних полей —
образ, записанный старой версией прошивки, читается без сдвига.

Начальное время RTC из КУ «Задание настроек» (миллисекунды + секунды)
хранится в MRAM и ставится на часы при загрузке (`action_load_mram`): приборное
время программное и после каждого сброса начинается с нуля, так что оно
стартует с этого значения. Сама КУ 8 на часы сразу не действует; в ходе работы
часы ставят КУ «Предустановка времени» (`0x0F02`) и `0x0401`. Миллисекунды ≥ 1000
в КУ 8 отклоняются квитанцией `ERR_CONTENT`. Документ момент применения не
оговаривает — принятое толкование, `docs/OPEN_ISSUES.md` §9.6.

Результаты теста лежат в отдельных областях и адресуются не смещением, а парой
«копия + банк» через `board_mram_write_test_result` / `_read_test_result`.
Раскладку по адресам держит `BSP/Board_API/src/board_api.c`
(`0x2000` для банка 1, `0x4000` для банка 2), уровню `Algorithm` она не видна.
Размер образа — 6144 байта `Nerr` + 2 байта CRC.

`Nerr` пакуется по 24 бита на блок (2048 блоков), значения выше `0xFFFFFF`
насыщаются. Проверка размера — `_Static_assert` в начале файла.

Если обе копии не проходят CRC, поднимается `ALARM_MRAM`. Записи заводского
образа по умолчанию нет.

## 11. Аварии

`Algorithm/include/alarm.h`. 16 признаков:


| Бит | Имя           | Бит | Имя           |
| -----: | ---------------- | -----: | ---------------- |
|      0 | `ALARM_MC_TEMP`  |      8 | `ALARM_PED_PS`   |
|      1 | `ALARM_PU_TEMP`  |      9 | `ALARM_PED_DIR`  |
|      2 | `ALARM_PED_TEMP` |     10 | `ALARM_PED_ST`   |
|      3 | `ALARM_BD_TEMP`  |     11 | `ALARM_NAND_PS`  |
|      4 | `ALARM_PU_VOLT`  |     12 | `ALARM_NAND_PR`  |
|      5 | `ALARM_PU_CURR`  |     13 | `ALARM_USB_VBUS` |
|      6 | `ALARM_PED_VOLT` |     14 | `ALARM_USB_PR`   |
|      7 | `ALARM_PED_CURR` |     15 | `ALARM_MRAM`     |

`masked_alarm = alarm_status & alarm_mask`. Немаскируемые биты (`NAND_PS`,
`NAND_PR`, `USB_PR`) принудительно добавляются в маску функцией
`alarm_sanitize_mask()`.

### Обнаружение

`Algorithm/src/alarm_monitor.c`. Две функции постановки признака:

```c
void alarm_set(SystemContext *ctx, uint32_t bit);    /* только выставить бит  */
void alarm_raise(SystemContext *ctx, uint32_t bit);  /* + событие на фронте   */
```

`alarm_raise` ставит `EVENT_MASKED_ALARM_SET` только на переходе
`masked_alarm` из нуля в ненулевое значение. Благодаря этому режим `ALARM`, в
котором контроль продолжает работать, не заваливает очередь повторами.
`alarm_set` используется там, где результат действия и так возвращает
`ACTION_ALARM` и переход выполнит автомат.

`alarm_monitor_poll(ctx, now_ms)` вызывается из главного цикла, срабатывает раз
в 20 с и только в режимах DUTY, ERASE, TEST, OBSERVE, DUMP, ALARM. Параметр
проверяется, лишь если чтение вернуло `BOARD_OK` и признаки `ready` /
`range_valid` взведены — отсутствующий или неисправный датчик не даёт ложной
аварии. С порогами контроль сравнивает, только когда они загружены
(`SystemContext.thresholds_loaded`: настройки из MRAM при старте или КУ 8). До
этого пороги нулевые, и любое показание было бы «вне диапазона»; проверки
подтверждения питания ПЭД и NAND идут всегда.

### Что откуда берётся


| Биты                                        | Признак                                        | Состояние                                                    |
| ------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------- |
| 1, 2                                              | Температура ПУ и ПЭД                | контроль 20 с по I2C                                     |
| 4, 5, 6, 7                                        | Напряжение и ток ПУ и ПЭД     | контроль 20 с по I2C                                     |
| 8, 11                                             | Питание ПЭД и банка NAND        | контроль 20 с + точки включения питания |
| 0, 3                                              | Температура МК и блока детекторов | контроль 20 с по АЦП (`board_read_analog_temps`): МК — встроенный датчик ADC1_IN17 с калибровками TS_CAL1/TS_CAL2, БД — TC1047 на ADC12_IN5; пороги — `mcu_pu_temp_*` и `det_temp_*` конфигурации |
| 8, 9, 10                                          | Питание, готовность и статус ПЭД | процедура включения ПЭД и защёлки драйвера `PED_REG` (`board_ped_take_faults`), собираются во всех режимах кроме INIT (`algorithm_collect_hw_events`); на настоящей ПЭД не проверены |
| 15                                                | MRAM при старте                 | обе копии невалидны, сбой восстановления копии или чтения конфигурации / служебных данных |

| 14                                                | Сбой вывода данных (USB / FTDI) | ошибка `board_data_write` в DUMP, ошибка досылки при завершении, таймаут передачи `DUMP_MODE_TX_TIMEOUT_S` |
| 15                                                | Ошибка MRAM в работе | чтение или запись служебных данных, конфигурации (КУ 8), результатов теста (`Nerr`), карты плохих блоков; при сбое чтения служебные данные **не перезаписываются** |

Биты 8 и 11 выставляются двумя способами: циклом контроля, когда питание
числится включённым, но читается выключенным, и в момент включения
(`prepare_single_nand_bank`, `confirm_ped_powered`), когда `PSON` не
подтвердился — там действие возвращает `ACTION_ALARM`.

### Политика аварий (по «Порядку работы с интерфейсами» v2)

- **Старт без аварий.** `action_load_mram` обнуляет «Аварийный статус» и
  `MaskedAlarm`; сохранённый в MRAM статус не восстанавливается. Если неисправность
  осталась, её снова обнаружит контроль 20 с или следующая операция.
- **Сбой MRAM при старте** (`action_check_mram`, `action_restore_mram_copy`,
  `action_load_mram`) → `ALARM_MRAM` и режим ALARM. Сбой инициализации CAN
  (`EVENT_INIT_FAIL`) — режим ALARM без признака MRAM.
- **Пустая MRAM** (обе копии невалидны; в полёте исключено): старт → ALARM с
  `ALARM_MRAM`, маска до загрузки конфигурации — все биты. КУ «Сброс аварий» из
  ALARM не выводит, пока MRAM пустая. КУ 8 записывает конфигурацию и обнулённые
  служебные данные (оба банка «требуют стирания», счётчики из слова управления
  записью КУ 8), снимает `ALARM_MRAM` → DUTY. Пока настроек нет, контроль 20 с
  с порогами не сравнивает, поэтому ложных аварий температуры и питания за время
  ожидания КУ 8 не появляется.
- **ТС «Телеметрия» при сбое чтения MRAM** уходит с порогами и маской из ОЗУ
  (те, с которыми работает прошивка), служебные счётчики — нули, ставится
  `ALARM_MRAM`.
- **Датчики I2C** (TMP112, INA219) инициализируются при первом чтении и заново
  после ошибки. Датчики ПЭД контроль 20 с опрашивает, только когда ПЭД включена.
- **ALARM только по активной аварии.** Если действие вернуло `ACTION_ALARM`, но
  выставленный бит выключен маской, автомат в ALARM не уходит: КУ получает
  ACK «другое», запуск режима не выполняется (остаёмся в DUTY), выход из режима
  выполняется как обычно. Немаскируемые `NAND_PS`, `NAND_PR`, `USB_PR` всегда
  активны.
- **Процедура включения ПЭД продолжается**, если `PED_PS` / `PED_DIR` / `PED_ST`
  замаскирован: бит ставится в статус, наблюдение запускается.
- **Ошибки карты плохих блоков**: сбой MRAM → `ALARM_MRAM`, сбой NAND
  (сканирование, установка карты) → `ALARM_NAND_PR` (`nand_map_mram_failed()`).

### Аварии в режимах ERASE / TEST / DUMP

По протоколу CAN v2.1 (п. 5.2.3–5.2.7) авария — это признак в «Аварийном статусе»,
а из режимов 2, 3, 5 есть только выходы: штатно → DUTY, по КУ → DUTY / SHUTDOWN,
при аварии → ALARM. Правила реализации:

- **Признак ставится в месте обнаружения** (`alarm_raise` в `algorithm.c`):
  ошибка NAND → `ALARM_NAND_PR`, ошибка вывода данных → `ALARM_USB_PR`.
  Фронт `masked_alarm` даёт `EVENT_MASKED_ALARM_SET`, режим уходит в ALARM по
  обычному пути (`action_finish_*_alarm` + `enter_alarm`).
- **Завершение режима (`EVENT_*_DONE`) никогда не оставляет автомат в режиме.**
  Уборка банка (отключение линий и выключение по `power_after_done`) выполняется
  всегда, даже после ошибки; сбой уборки → `ALARM_NAND_PR`, сбой досылки DUMP →
  `ALARM_USB_PR`, сбой записи служебных данных / `Nerr` в MRAM → `ALARM_MRAM`.
  Затем: `masked_alarm != 0` → ALARM, иначе → DUTY (замаскированный признак
  остаётся виден в «Аварийном статусе»).
- **Сбой обмена с NAND на входе в режим** (Д-5, «Порядок работы», разд. 1):
  если микросхема не ответила при подключении банка (`board_nand_connect`) или
  при запуске стирания, теста, чтения (`board_nand_erase_start`,
  `board_nand_get_capacity_packets`, `board_nand_open_read`), ставится
  `ALARM_NAND_PR`, банк отключается и выключается, КУ получает ACK «другое»,
  автомат уходит в ALARM. Ошибка аргумента (`BOARD_ERR_INVALID_ARG`) — ошибка
  прошивки, а не обмена: ACK «содержание», без аварии. При отказе на входе в
  DUMP канал вывода закрывается (`board_data_link_close`).
- **Вход в ALARM без признака исключён:** если операция режима помечена
  неуспешной, а активного признака нет, на завершении ставится `ALARM_NAND_PR`.
- **Таймаут передачи DUMP:** на каждом `EVENT_RTC_1HZ` в стадии отправки
  проверяется продвижение. Секунда считается простоем, только если с прошлого
  тика режим пытался отправить данные (`tx_attempted`): тики, накопившиеся, пока
  главный цикл был занят, и пришедшие пачкой, таймаут не вызывают.
  `DUMP_MODE_TX_TIMEOUT_S` (5) таких секунд без единого принятого байта →
  `ALARM_USB_PR`.
- **Не аварии:** E_Fail при стирании (блок уходит в карту плохих), несовпадения
  в TEST (результат теста, `Nerr`), неисправимая ошибка ECC при DUMP — пакет
  выводится как есть, у пакета НИ свой CRC16, его проверяет наземный комплекс.

`ALARM_NAND_PR` и `ALARM_USB_PR` немаскируемые, поэтому сбой NAND или вывода
данных всегда приводит в ALARM. `ALARM_MRAM` маскируемый.

### Выключение (режим 7)

`action_start_shutdown`: служебные данные записываются в MRAM, ПЭД и оба банка
NAND выключаются, затем отключаются линии (Z-состояние, Д-5): ПЭД, NAND1, NAND2,
SPI1/SPI3 MRAM (`BOARD_SIGNAL_MRAM`: `spi_deinit_bus` и NSS, SCK, MISO, MOSI в
аналоговый режим) и I2C1–I2C3 (`BOARD_SIGNAL_I2C`). После этого к MRAM и I2C
никто не обращается: в SHUTDOWN допустимы только «Запрос статуса» (выводы GPIO)
и «Запрос версии», контроль 20 с выключен, адреса из КУ 0F0E/0F0F в MRAM не
пишутся. Выход из режима — только снятием питания. ADC12_IN5 всегда в
аналоговом режиме.

Слово «Статус НА» (`board_read_power_status`, байты 4–5 ТС «Статус»): биты 10–12
`PU_FTDI_PS`, `PU_FTDI_PSON`, `PU_FTDI_RES` заполняются в сборках с FTDI; без FTDI
равны 0 (протокол v2.1, табл. «Статус НА», прим. 1).

Приёмник данных (п. 10–11 «Порядка работы»): перед DUMP читается `PU_USB_VBUS`
(`HIGH` — не подключён) → `ALARM_USB_VBUS`; если признак не замаскирован, DUMP не
начинается (ACK «другое», переход в ALARM). Затем `board_data_link_open`. Во время
DUMP фронт `PU_USB_VBUS` → `ALARM_USB_VBUS`. При `ALARM_USB_VBUS` / `ALARM_USB_PR`
интерфейс выключается (`board_data_link_close`: линии, Reset и питание FTDI) и
включается снова следующим DUMP.

### Единицы температуры, тока и напряжения

Протокол v2.1 и формат НИ v6.1 масштаб не указывают: поля названы просто
«Температура …», «Ток …». Единицы заданы владельцем 2026-11-05:

| Величина | Единица на шине | Тип | Board_API |
|---|---|---|---|
| Температура (МК, ПУ, ПЭД, БД) | 0,01 °C | `int16` (±327,67 °C) | милли-°C |
| Напряжение (ПУ, ПЭД) | мВ | `uint16` | мВ |
| Ток (ПУ, ПЭД) | мА | `uint16` | мкА |

Одни и те же единицы — в порогах КУ «Задание настроек», настройках MRAM в ТС
«Телеметрия», полях измерений ТС «Телеметрия» и формата НИ «Телеметрия».
Пересчёт: `transport_temp_milli_to_centi` (милли-°C / 10, с отбрасыванием дробной
части), `transport_current_ua_to_ma` (мкА / 1000, отрицательный ток → 0) в

## 12. Режим наблюдений

Решения, которые документы оставляют открытыми, собраны в
`docs/OBSERVE_ASSUMPTIONS.md` (раздел «Режим», M1–M10).

### Поток данных

```
 прерывания (ped_reg)                    проход суперцикла, observe_poll()
 PED_TG  → событие   ─┐                  1. ≤ 64 записей из кольца (пачками по 16):
 RTC_OUT → секунда    ├→ кольцо 2048        событие → observe_science_on_event
           + счётчики ┘                     секунда → observe_science_on_second (+ «Телеметрия»)
                                         2. отложенные КТ → форматы 05h / 06h / 07h
                                         3. ni_writer_poll: пакет → NAND
 неисправности ПЭД → аварии — в algorithm_collect_hw_events, во всех режимах
```

Если в потоке пакетов нет места (`OBSERVE_SCIENCE_NO_ROOM`), запись не теряется:
она остаётся в пачке и обрабатывается на следующем проходе, кольцо перестаёт
освобождаться, и ПЭД ждёт (D7). Без готового пакета `ni_writer` опрашивает NAND
не чаще раза в `NI_WRITER_IDLE_POLL_US` (50 мкс, `board_elapsed_us`).

### Этапы (`ObserveStage`)

| Этап | Что происходит |
|---|---|
| `ENTER` | После КУ 4 (квитанция сразу): банк NAND включён и подключён, карта плохих блоков загружена, ПЭД настроена по битам 2–4 и регистрам 80h/81h. `ni_writer` ищет место продолжения (по шагу за проход). Затем номер сеанса +1 (сразу в MRAM), `ni_stream_begin`, `observe_science_begin` (Bmin/Lmin/Lmax/n(AC1)max из MRAM), `board_ped_acquisition_start` → `ACTIVE`. |
| `ACTIVE` | Поток данных выше. КУ 5: биты 2–4 и регистры ПЭД — сразу, параметры — со следующей секунды (T4). |
| `FINISHING` | После КУ 6 / «Выключение» (квитанция сразу): ждём следующую отметку секунды, на ней пишутся «Счетчики», «Спектр» и «Телеметрия». Без отметки за `OBSERVE_FINISH_TIMEOUT_S` (3) тиков RTC — завершение без них. |
| `FLUSHING` | Сбор остановлен, последний пакет дополнен AAAAh, `ni_writer` дописывает и сохраняет счётчик в MRAM → `EVENT_OBSERVE_DONE` → ПЭД и банк по битам КУ 6 → DUTY (или SHUTDOWN), ТС «Статус». |
| `EXIT_FULL` | Банк заполнен (`ni_writer` → FULL) → `EVENT_NAND_FULL`: сбор остановлен, банк по биту 5, ПЭД по битам 6–7 КУ 4, признак «банк полон» → DUTY. |
| `EXIT_ALARM` | Сбой записи NAND → `ALARM_NAND_PR`, сбой MRAM → `ALARM_MRAM`; неисправности ПЭД → `ALARM_PED_PS` / `_DIR` / `_ST`. Незамаскированная авария → недописанный пакет отбрасывается (P2) → ALARM. |

КУ 6 на этапе `ENTER` (сеанс ещё не начат) завершает режим сразу.

Формат «События» не пишется, пока в сеансе не принята хотя бы одна КТ (любая из
трёх), — решение владельца, в документах его нет (E6 в `OBSERVE_ASSUMPTIONS.md`).
Флаг CMake `NATALIA_OBSERVE_EVENTS_WAIT_KT`, по умолчанию ON; OFF — «События»
пишутся сразу по параметрам наблюдений.

### Счётчик пакетов и место продолжения записи

В служебных данных MRAM на каждый банк хранятся: число записанных пакетов, CRC
последнего пакета, номер последнего выведенного пакета, признак «банк полон»;
общий — номер сеанса наблюдений.

- **Когда пишется в MRAM.** `ni_writer` сохраняет счётчик и CRC каждые
  `NI_WRITER_MRAM_SAVE_PERIOD` (128) пакетов, при заполнении банка и при
  штатном завершении сеанса — в последнем случае точное значение. Сохранение
  выполняется только после того, как NAND подтвердила запись, поэтому значение в
  MRAM никогда не больше реального.
- **Как находится место продолжения** (этап `ENTER`, `ni_writer_begin` →
  `ni_writer_recover_step`). Банк заполняется строго подряд, после ERASE всё за
  последним записанным пакетом стёрто (`FFh`). Значит, «записано, записано, …,
  стёрто, стёрто» — и первый стёртый пакет ищется двоичным поиском на отрезке
  [счётчик из MRAM, ёмкость): ≤ 18 чтений пакета на банк 262144 пакетов, по одному
  за проход суперцикла. Если найденная позиция совпала со счётчиком MRAM, CRC
  берётся из MRAM; иначе (питание пропало между сохранениями, отставание до 127
  пакетов) — читается последний записанный пакет и берётся его CRC. Номер пакета
  и цепочка CRC продолжаются без разрыва.
- **ERASE и TEST.** Оба уничтожают содержимое банка, поэтому при их запуске банк
  помечается «требует стирания»: счётчик, CRC и номер выведенного пакета — 0,
  признак «банк полон» — 1 (в MRAM и в ОЗУ). Снимает пометку только завершённый
  ERASE или завершённый без ошибки TEST (финальное стирание). Прерванный по КУ,
  по аварии или пропаданием питания режим оставляет пометку — OBSERVE на этот банк
  отвечает «ошибка содержимого», пока банк не стёрт заново. Иначе двоичный поиск
  работал бы на «рваной» картине (стёртые блоки вперемешку со старыми данными
  или тестовыми шаблонами). В ТС «Статус» на время ERASE / TEST банк показан
  полным.
- **Номер сеанса** загружается из MRAM при старте (`action_load_mram`) и
  увеличивается на 1 перед каждым сеансом.
- **Телеметрия.** В режиме OBSERVE счётчик пакетов активного банка в ТС
  «Телеметрия» — живой (`committed_packet_count`), в остальных режимах — из MRAM.
- **Ограничение.** Если питание пропало посреди программирования страницы,
  недописанный пакет поиск считает записанным, и его CRC попадёт в цепочку как
  «предыдущий». Пакет сам будет с неверным CRC, его отбракует наземный комплекс.
- **DUMP «всё»** берёт число пакетов из MRAM. После пропадания питания посреди
  сеанса последние ≤ 127 пакетов в него не попадут до следующего запуска OBSERVE,
  который восстановит точный счётчик.

### Формат «Телеметрия»

Измерения те же, что в ТС «Телеметрия» (`transport_read_measurements`); статус
ПЭД читается из ПЭД, если она включена. В ТС «Телеметрия» в режиме наблюдений
заполняются байты 30–35: статус ПЭД (младшее слово), конфигурация триггера,
параметры наблюдений.

## 13. Хостовая заглушка Board_API

`Algorithm/src/board_api_stub.c`, включается флагом `NATALIA_USE_BOARD_STUBS=ON`.
Реализует **все** функции `board_api.h`, поэтому уровень `Algorithm` собирается
и работает на обычном ПК.

Поведение по каждой функции — в [`Board_API.md`](Board_API.md), раздел
«Поведение хостовой заглушки». Здесь — то, что важно при написании тестов.

### Параметры модели


| Параметр          |    Значение | Комментарий                                        |
| ------------------------- | ------------------: | ------------------------------------------------------------- |
| Банков NAND         |                   2 |                                                               |
| Ёмкость банка | **256 пакетов** | На плате — 262144. Хватает на два блока режима TEST. |
| Размер пакета |       2048 байт | Совпадает с полётным.                       |
| Копий MRAM           |                   2 |                                                               |
| Размер копии   |     1024 байта | Совпадает с полётным`BOARD_MRAM_COPY_SIZE`. |

### Что моделируется по-настоящему

- **NAND** — массив в ОЗУ. Запись пакетов, чтение по индексу и потоком,
  счётчик записанных пакетов, признак заполнения, стирание (заполнение `0xFF`),
  состояние питания банка.
- **MRAM** — два массива в ОЗУ, чтение/запись по смещению, копирование одной
  копии в другую.
- **Связь** — по одному слоту на приём и на передачу плюс счётчик переданных
  сообщений.
- **Датчики, часы и счётчики событий** — отдают то, что задал тест (см. ниже).

### Что упрощено до констант

Эти функции всегда возвращают `BOARD_OK` и фиксированное значение. Проверить
через них соответствующую логику **нельзя**:


| Функция                                      | Всегда возвращает                                      |
| --------------------------------------------------- | ---------------------------------------------------------------------- |
| `board_mram_check_crc`                              | `is_valid = 1` — копия всегда валидна               |
| `board_nand_erase_is_done`                          | `is_done = 1` — стирание мгновенное                 |
| `board_nand_write_poll` / `board_nand_write_flush`  | `is_idle` / `is_done` = 1                                              |
| `board_ped_read_status` / `board_read_power_status` | `0`                                                                    |
| `board_ped_read_event`                              | `bytes_read = 0`                                                       |
| `board_read_temp` (аналоговый канал)   | `25000` м°C                                                          |
| `board_usb_write` / `board_data_write`              | принято всё,`bytes_written = size`                           |
| `board_usb_is_ready` / `board_data_is_ready`        | `1`                                                                    |

Путь «обе копии MRAM испорчены -> `ALARM_MRAM`» и таймауты стирания хостовыми
тестами не покрываются и покрыты быть не могут без доработки заглушки.

Всё, чем тест может управлять извне:

  тестового бинарника данные переносятся из теста в тест. Либо задавайте
  исходное состояние явно, либо учитывайте порядок вызовов.

## 14. Как выглядит хостовый тест

Общий шаблон (по `tests/test_erase.c`):

```c
static void begin_test(SystemContext *ctx, SystemState state) {
    memset(ctx, 0, sizeof(*ctx));
    ctx->state = state;
    ctx->previous_state = state;
    ctx->nand1.bank = NAND_BANK_1;
    ctx->nand2.bank = NAND_BANK_2;

    system_event_queue_init();
    board_comm_stub_reset();
    transport_reset();          /* иначе состояние TX течёт между тестами */
}
```

Дальше — два способа подачи воздействия:

```c
/* 1. Через протокол: проверяется и разбор transport, и автомат */
board_comm_stub_inject_rx(0x0F08U, ADDR_BVS, ADDR_NA, payload, 6U);
transport_poll(&ctx, 0U);
algorithm_process_events(&ctx);

/* 2. Напрямую событием: проверяется только автомат */
SystemEvent event = { .type = EVENT_CMD_ERASE };
event.command.erase.bank = NAND_BANK_1;
system_event_queue_push_back(&event);
algorithm_process_events(&ctx);
```

Длительные режимы прокручиваются циклом со счётчиком-предохранителем — так
тест не зависнет, если режим не завершится:

```c
for (guard = 0U; (guard < 100U) && (ctx->state != STATE_DUTY); ++guard) {
    algorithm_poll(ctx);
    algorithm_process_events(ctx);
}
assert(ctx->state == STATE_DUTY);
```

Проверки — по `SystemContext`, по содержимому MRAM через `mram_store_*` и по
последнему переданному сообщению через `board_comm_stub_last_tx()`.

Тесты используют `assert()` и возвращают `0` из `main()`; регистрация — в
`tests/CMakeLists.txt`.

### Запуск

```bash
cmake -S . -B cmake-build-tests -G Ninja \
  -DNATALIA_BUILD_TESTS=ON \
  -DNATALIA_USE_BOARD_STUBS=ON

cmake --build cmake-build-tests -j 18
ctest --test-dir cmake-build-tests --output-on-failure
```

## 16. Правила уровня

- C11, без C++, без `malloc`/`free`, без динамической памяти.
- Обращение к аппаратуре — только через `board_api.h`.
- `handle_event()` вызывается только из `algorithm_process_events()`.
  Исключение — точечные тесты автомата.
- Поллеры режимов не вызывают `handle_event()`, а ставят события в очередь.
- Обработчики прерываний не трогают `SystemContext` и не вызывают `action_*`.
- Длительные операции кооперативные: ограниченная работа за вызов.
- При изменении `board_api.h` правятся **обе** реализации — прошивочная
  `BSP/Board_API/src/board_api.c` и хостовая `Algorithm/src/board_api_stub.c`.
