# Natalia Core

Прошивка платы управления гамма-детектором на базе STM32L496.

Проект пишется на чистом C с использованием CMSIS, без HAL/LL. Основной принцип архитектуры: алгоритм работы прибора отделён от низкоуровневого доступа к аппаратуре.

---

## 1. Структура проекта

```text
natalia-core/
├── Algorithm/
├── BSP/
├── Core/
├── Device/
├── Drivers/
├── Diagnostics/
├── main.c
├── CMakeLists.txt
└── Toolchain_STM32L4.cmake
```

### `Algorithm/`

Алгоритмический уровень прибора:

- автомат состояний и переходов между режимами;
- обработка событий и команд управления;
- действия, выполняемые в режимах;
- транспортный слой КУ/КТ/ТС;
- логическая работа с конфигурацией и служебными данными MRAM.

`Algorithm` не обращается напрямую к регистрам STM32. Доступ к аппаратуре выполняется через `board_api`.

### `BSP/`

Низкоуровневая работа с периферией STM32 и сигналами платы.

```text
BSP/
├── Board_API/
├── CAN/
├── GPIO/
├── RTC/
└── UART/
```

- `GPIO/` — конфигурация и управление выводами МК.
- `RTC/` — аппаратные часы, `RTC_OUT` 1 Гц, секундные события, чтение и предустановка приборного времени.
- `CAN/` — драйвер CAN1: настройка, RX/TX-очереди, IRQ, фиксация результата передачи и ошибок.
- `UART/` — отладочный вывод через LPUART.
- `Board_API/` — firmware-реализация аппаратных функций, которые вызывает алгоритм.

Принцип разделения файлов интерфейса:

```text
*_config.c / *_private.h
    Внутренняя конфигурация периферии:
    clock enable/reset, GPIO Alternate Function, регистры, IRQ, режимы работы.

*.c / *.h
    Публичный рабочий интерфейс:
    init, send/receive, get/set, обработка событий и результатов.
```

Внешний код не должен подключать `*_private.h` и обращаться к деталям конфигурации периферии.

### `Core/`

Общие компоненты прошивки:

- настройка системного тактирования;
- системная временная база;
- общие статусы;
- тип приборного времени.

### `Device/`

Описание конкретной платы и микроконтроллера:

- карта выводов `board_pins`;
- конфигурация аппаратного варианта платы `board_config`;
- startup-файл;
- linker script;
- системные файлы STM32.

В текущем Nucleo-варианте используется:

```text
HSI16 -> PLL -> SYSCLK 80 MHz
```

Для целевой платы предусмотрен переход на:

```text
HSE 8 MHz -> PLL -> SYSCLK 80 MHz
```

При этом частоты шин и настройка CAN сохраняются.

### `Drivers/`

Драйверы устройств и протоколов поверх BSP.

```text
Drivers/
└── UniCAN/
```

`UniCAN/` отвечает за:

- упаковку и распаковку сообщений UniCAN;
- короткие и длинные сообщения;
- CRC16 XMODEM;
- timeout незавершённых RX-сообщений;
- подтверждённую передачу TX-сообщений;
- timeout и завершение неудачной передачи.

UniCAN не работает напрямую с регистрами STM32. Связь с аппаратным CAN1 выполняется через `unican_port`.

### `Diagnostics/`

Диагностические функции для стендовой проверки.

Поддерживается вывод логических сообщений UniCAN через UART:

```text
DSTLOG|v=1|src=detector|ts=...|dir=rx|id=...|data=...
DSTLOG|v=1|src=detector|ts=...|dir=tx|id=...|data=...
```

В конечной прошивке диагностический вывод должен быть отключён.

## 2. Сборка и запуск

### Основные CMake-флаги


| Флаг                            | Назначение                                                                                                                                                                   |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NATALIA_BUILD_TESTS`               | Сборка тестового варианта без запуска firmware на плате.                                                                                       |
| `NATALIA_USE_BOARD_STUBS`           | Использовать заглушки`board_api` вместо реального железа.                                                                                     |
| `NATALIA_ENABLE_DEBUG_LOG`          | Включить отладочный вывод через LPUART.                                                                                                                    |
| `NATALIA_ENABLE_DETECTOR_PROTO_LOG` | Включить машинно-читаемый вывод`DSTLOG` для проверки UniCAN. Требует `NATALIA_ENABLE_DEBUG_LOG=ON` и `NATALIA_ENABLE_UNICAN_DRIVER=ON`. |
| `NATALIA_ENABLE_UNICAN_DRIVER`      | Собрать драйвер UniCAN.                                                                                                                                                  |
| `NATALIA_ENABLE_PED_REG_DRIVER`     | Собрать драйвер PED_REG; пока выключен.                                                                                                                      |
| `NATALIA_ENABLE_USB_DEVICE_DRIVER`  | Собрать USB Device; пока выключен.                                                                                                                                  |
| `NATALIA_NAND_PS_OFF_LEVEL`         | Уровень выключения питания NAND; для текущей конфигурации используется`HIGH`.                                                |

### Сборка с железом

Текущий рабочий стендовый вариант для Nucleo, CAN1, RTC и UniCAN:

```bash
rm -rf cmake-build-debug

cmake -S . -B cmake-build-debug \
  -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=Toolchain_STM32L4.cmake \
  -DNATALIA_BUILD_TESTS=OFF \
  -DNATALIA_USE_BOARD_STUBS=OFF \
  -DNATALIA_ENABLE_DEBUG_LOG=ON \
  -DNATALIA_ENABLE_DETECTOR_PROTO_LOG=ON \
  -DNATALIA_NAND_PS_OFF_LEVEL=HIGH \
  -DNATALIA_ENABLE_UNICAN_DRIVER=ON \
  -DNATALIA_ENABLE_PED_REG_DRIVER=OFF \
  -DNATALIA_ENABLE_USB_DEVICE_DRIVER=OFF

cmake --build cmake-build-debug --target natalia_firmware -j 18
```

Для финальной сборки без отладочного UART-вывода:

```bash
-DNATALIA_ENABLE_DEBUG_LOG=OFF
-DNATALIA_ENABLE_DETECTOR_PROTO_LOG=OFF
```

На текущем этапе аппаратный запуск использует тестовый `main.c`, который вручную создаёт контекст в `STATE_DUTY`. Это сделано только для проверки RTC/CAN/UniCAN/transport. Полноценный старт через `EVENT_BOOT` будет подключён после реализации MRAM.

### Сборка без железа

Вариант без платы предназначен для проверки логики `Algorithm` с использованием заглушек аппаратуры:

```bash
rm -rf cmake-build-tests

cmake -S . -B cmake-build-tests \
  -G Ninja \
  -DNATALIA_BUILD_TESTS=ON \
  -DNATALIA_USE_BOARD_STUBS=ON \
  -DNATALIA_ENABLE_DEBUG_LOG=OFF \
  -DNATALIA_ENABLE_DETECTOR_PROTO_LOG=OFF \
  -DNATALIA_ENABLE_UNICAN_DRIVER=OFF \
  -DNATALIA_ENABLE_PED_REG_DRIVER=OFF \
  -DNATALIA_ENABLE_USB_DEVICE_DRIVER=OFF

cmake --build cmake-build-tests -j 18
```

Если тестовые executable зарегистрированы через CTest:

```bash
ctest --test-dir cmake-build-tests --output-on-failure
```

Без железа можно проверять автомат состояний и действия через stubs. Проверить реальные RTC, GPIO, CAN и UniCAN через такой запуск нельзя.

## 3. Что реализовано на данный момент

### Базовая инфраструктура

- embedded-сборка через CMake и `arm-none-eabi-gcc`;
- подключение CMSIS без HAL/LL;
- карта выводов платы;
- системное тактирование `SYSCLK = 80 MHz`;
- системная временная база;
- условный UART-debug вывод.

### GPIO и стартовая конфигурация

- основной CAN1 приводится в рабочее состояние;
- резервный CAN2 отключается;
- линии питания и управления переводятся в безопасное стартовое состояние;
- неактивные на старте интерфейсы отключаются.

### RTC

Реализованы:

- работа RTC от LSE;
- аппаратный выход `RTC_OUT` 1 Гц;
- секундное событие и накопление непрочитанных тиков;
- чтение приборного времени;
- предустановка приборного времени.

### CAN1

Реализованы:

- выводы `PB8/PB9`, `AF9`;
- скорость `500 kbit/s`;
- приём и передача сырых CAN-кадров;
- RX/TX-очереди;
- прерывания CAN;
- контроль успешного завершения TX;
- timeout и abort зависшей передачи.

### UniCAN

Реализованы:

- короткие сообщения;
- длинные сообщения;
- CRC16 XMODEM;
- сборка входящих длинных сообщений;
- timeout незавершённого RX-сообщения;
- подтверждённая отправка исходящих сообщений;
- timeout исходящего сообщения.

### Связь с алгоритмом

Через `Algorithm/transport.c` подключены:

- КУ `0002h` — предустановка времени;
- КУ `0001h` — запрос статуса;
- ТС `0201h` — квитанция;
- ТС `0200h` — статус;
- очередь исходящих ТС;
- повторная отправка ТС при ошибке передачи UniCAN.

Проверен путь:

```text
CAN1 -> UniCAN -> transport -> state/actions -> board_api -> RTC/GPIO
     -> transport -> UniCAN -> CAN1
```

## 4. Что изменено и исправлено в `Algorithm`

- Протокольная логика отделена от `board_api`: упаковка КУ/ТС находится в `transport.c`.
- Формат времени приведён к структуре `seconds + milliseconds`, соответствующей CAN-протоколу.
- Команда предустановки времени подключена к реальному RTC.
- Реализованы квитанция и статус.
- Добавлена очередь исходящих ТС: одна команда может формировать несколько ответов подряд.
- Добавлен retry исходящих ТС при ошибке UniCAN: первоначальная попытка и до трёх повторов.
- Исправлен расчёт замаскированного аварийного статуса:

```c
masked_alarm = alarm_status & alarm_mask;
```

- Исправлена выдача статуса при выходе из аварийного режима после изменения конфигурации.
- Исправлена обработка заполнения NAND в режиме наблюдений:
  - устанавливается флаг заполнения банка;
  - останавливается регистрация событий;
  - обновляются служебные данные;
  - после перехода в дежурный режим выдаётся новый статус.

Полноценный запуск алгоритма через `EVENT_BOOT` пока не используется, потому что работа с MRAM ещё не подключена.

## 5. Следующий шаг

### 5.1. По железу

Следующий аппаратный этап — работа с памятью.

План:

1. NAND/QSPI для режимов наблюдения, стирания, тестирования и вывода данных.
2. Реализовать доступ к MRAM.
3. Подключить чтение и запись конфигурации и служебных данных.
4. Реализовать проверку CRC и восстановление резервной копии MRAM.
5. Перейти от тестового запуска в `STATE_DUTY` к реальной инициализации через `EVENT_BOOT`.

### 5.2. По алгоритму

#### 1. Движки длительных операций (TEST, DUMP, ERASE) — [Дмитрий]

**В чем суть:** Сейчас верхнеуровневый автомат (`state.c`) умеет запускать эти режимы и переключать их стадии, но сам процесс (запись тестовых паттернов или выкачивание логов по USB) физически не происходит.
**Задача:** Написать неблокирующие (non-blocking) фоновые обработчики, которые будут вызываться в главном цикле `main()` и двигать процесс шаг за шагом.

* **Режим TEST:** Реализовать генератор тестового паттерна. Логика: записали блок через `board_nand_write()` -> прочитали -> побайтово сравнили -> записали количество ошибок в массив `Nerr`.
* **Режим DUMP:** Чтение пакетов через `board_nand_read()` и отправка через `board_usb_write()`. Учесть логику повторной попытки при ошибке передачи.
* **Режим ERASE:** Фоновый опрос статуса очистки чипа.
* **Архитектурное требование:** Прибор не должен зависнуть в цикле стирания или тестирования. Обработчик должен сделать один небольшой шаг (например, обработать один блок памяти), вернуть управление, и продолжить работу на следующей итерации `main()`. По завершении процесса — сгенерировать событие (например, `EVENT_TEST_DONE`), чтобы автомат состояний корректно вернулся в дежурный режим.

#### 2. Формирование Научной Информации (НИ) — [Мария]

**В чем суть:** Физические события уже посчитаны модулем ПЭД, цель — упаковать их в жестко заданные спецификацией форматы и пакеты.
**Задача:** Собрать пакеты для записи в память и отправки на Землю.

* Раз в секунду (по событию `EVENT_RTC_1HZ`) забирать готовые данные у модуля ПЭД (Счетчики, Спектр) и актуальную телеметрию.
* Упаковывать эти данные в строгие пакеты размером ровно **2048 байт** (1024 16-битных слова).
* Добавлять маркерные слова, ID сеансов, номера пакетов. Реализовать логику добивки неполного последнего пакета словами `AAAAh` при штатном завершении наблюдений.
* Готовые пакеты отдавать на запись через `board_nand_write()`.
* **Архитектурное требование:** Аппаратный подсчет контрольных сумм (CRC) берет на себя железо (через `board_api`). Твоя задача — просто резервировать правильные поля в структуре пакета НИ под эту CRC согласно спецификации.
