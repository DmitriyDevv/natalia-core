# Natalia Core

Прошивка платы управления гамма-детектором НА NATALIA на базе STM32L496ZGTX
(Cortex-M4F).

Проект написан на чистом **C11** поверх **CMSIS**, без HAL и LL. Основной принцип
архитектуры — строгое разделение уровней: алгоритм работы прибора отделён от
низкоуровневого доступа к аппаратуре.

---

## 1. Архитектура и уровни

Правило проекта — соблюдать разделение уровней:

```text
main / tests / bring-up main'ы
    -> Algorithm            (автомат состояний, действия, transport, MRAM-store)
        -> Board_API        (единственный аппаратный контракт для Algorithm)
            -> BSP / Drivers (периферия STM32, UniCAN)
                -> регистры
```

`Algorithm` **не обращается** напрямую к регистрам, GPIO, I2C, SPI, QSPI, RTC,
USB, CAN, ADC, DMA, к внутренностям PED_REG/INA219/TC1047 или к IRQ. Любой доступ
к аппаратуре идёт только через `BSP/Board_API/include/board_api.h`. Полное
описание контракта — в [`Board_API.md`](Board_API.md).

Верхний уровень построен на событиях: центральная функция
`handle_event(ctx, event)` обрабатывает ровно одно событие, а события приходят
через централизованную очередь фиксированного размера. Длительные операции
(TEST/ERASE/DUMP/OBSERVE) выполняются кооперативно: каждый шаг поллера делает
ограниченную работу и возвращает управление, а по завершении ставит в очередь
событие (`EVENT_TEST_DONE`, `EVENT_ERASE_DONE`, `EVENT_DUMP_DONE`, …).

## 2. Структура проекта

```text
natalia-core/
├── Algorithm/        Автомат состояний, действия, transport, MRAM-store
├── BSP/              Периферия STM32 и Board_API
│   ├── Board_API/    Аппаратный контракт для Algorithm (+ хостовые заглушки)
│   ├── CAN/          Драйвер CAN1
│   ├── I2C/          I2C (INA219, TMP112)
│   ├── SPI/          SPI для MRAM (+ DMA)
│   ├── QSPI/         QSPI для NAND (+ DMA)
│   ├── ADC/          ADC (TC1047)
│   ├── USB_OTG_FS/   USB CDC (вывод данных в DUMP)
│   ├── GPIO/ RTC/ UART/ ...
├── Core/             Тактирование, временная база, статусы, CRC16
├── Device/           Карта выводов, конфигурация платы, startup, linker
├── Drivers/
│   └── UniCAN/       Протокол UniCAN поверх CAN1
├── Diagnostics/      Диагностический вывод для стенда (DSTLOG)
├── tests/            Хостовые тесты (Algorithm через заглушки)
│   └── firmware/     Стендовые bring-up main'ы (по одному на периферию)
├── main.c            Прошивочный main по умолчанию
├── Board_API.md      Документация аппаратного контракта Board_API
├── CMakeLists.txt
└── Toolchain_STM32L4.cmake
```

## 3. Требования к окружению

- `arm-none-eabi-gcc` (сборка прошивки под Cortex-M4F);
- системный `gcc`/`clang` (хостовые тесты);
- `cmake` >= 3.20;
- `ninja`.

## 4. Сборка без железа (хостовые тесты)

Проверка логики `Algorithm` на заглушках `board_api` — не требует платы и
кросс-компилятора. Это основной способ регрессионной проверки.

```bash
cmake -S . -B cmake-build-tests -G Ninja \
  -DNATALIA_BUILD_TESTS=ON \
  -DNATALIA_USE_BOARD_STUBS=ON

cmake --build cmake-build-tests -j 18
ctest --test-dir cmake-build-tests --output-on-failure
```

Текущий набор тестов (`tests/`):


| Тест             | Что покрывает                                                               |
| -------------------- | --------------------------------------------------------------------------------------- |
| `test_state_machine` | Базовые переходы автомата                                        |
| `test_transport`     | Разбор КУ/КТ, сборка ТС, ТС 0203h (результаты теста) |
| `test_set_cfg`       | CMD_SET_CFG (0007h): декод, запись MRAM, маска аварий             |
| `test_mode_test`     | Режим TEST (0009h) на полном масштабе                              |
| `test_erase`         | Режим ERASE (0008h)                                                                |
| `test_dump`          | Режим DUMP (0006h): вывод по USB, ACK, служебные данные      |
| `test_shutdown`      | Режим SHUTDOWN (0005h)                                                             |
| `test_mram_store`    | Загрузка/запись/восстановление MRAM, проверка CRC   |
| `test_observe`       | Режим OBSERVE (частично; режим ещё не финальный)        |

Хостовая сборка проверяет автомат и действия. Реальные RTC/GPIO/CAN/UniCAN/NAND/
MRAM через неё проверить нельзя — для этого нужна прошивка (раздел 5).

## 5. Сборка прошивки (с железом)

Прошивка по умолчанию — `main.c`, стартует штатно через `EVENT_BOOT`
(инициализация аппаратуры -> проверка/восстановление/загрузка MRAM -> `DUTY`).

Рабочая сборка с включёнными проверенными на плате драйверами (CAN/UniCAN, NAND,
MRAM/SPI, I2C+INA219):

```bash
cmake -S . -B cmake-build-debug -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=Toolchain_STM32L4.cmake \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DNATALIA_BUILD_TESTS=OFF \
  -DNATALIA_USE_BOARD_STUBS=OFF \
  -DNATALIA_LOG_BACKEND=LPUART1 \
  -DNATALIA_ENABLE_DETECTOR_PROTO_LOG=ON \
  -DNATALIA_NAND_POWER_SWITCH=FPF2101 \
  -DNATALIA_ENABLE_UNICAN_DRIVER=ON \
  -DNATALIA_ENABLE_NAND_DRIVER=ON \
  -DNATALIA_ENABLE_MRAM_DRIVER=ON \
  -DNATALIA_ENABLE_SPI_DRIVER=ON \
  -DNATALIA_ENABLE_I2C_DRIVER=ON \
  -DNATALIA_ENABLE_INA219_DRIVER=ON

cmake --build cmake-build-debug --target natalia_firmware -j 18
```

> Тип сборки по умолчанию — `RelWithDebInfo` (`-O2 -g`). Не собирайте прошивку с
> `-O0`: путь данных (например, генерация паттернов NAND) работает в разы
> медленнее, и измерения пропускной способности теряют смысл.

Для финальной сборки без отладочного вывода:

```bash
-DNATALIA_LOG_BACKEND=NONE
-DNATALIA_ENABLE_DETECTOR_PROTO_LOG=OFF
```

## 6. CMake-флаги

Значения в скобках — умолчания.

### Режим сборки


| Флаг                           | Назначение                                                                                |
| ---------------------------------- | --------------------------------------------------------------------------------------------------- |
| `NATALIA_BUILD_TESTS` (OFF)        | Собрать хостовые тесты вместо прошивки.                           |
| `NATALIA_USE_BOARD_STUBS` (ON)     | Использовать хостовые заглушки`board_api` вместо железа.    |
| `NATALIA_FIRMWARE_MAIN` (`main.c`) | Какой`main` собирать (для стендовых bring-up main'ов — раздел 7). |

### Журнал и диагностика


| Флаг                                  | Назначение                                                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `NATALIA_LOG_BACKEND` (`LPUART1`)         | Бэкенд журнала:`NONE`, `LPUART1`, `USART2`, `FTDI`, `CAN`.                                                  |
| `NATALIA_ENABLE_DETECTOR_PROTO_LOG` (OFF) | Машинно-читаемый вывод`DSTLOG` для проверки UniCAN. Только для прошивки. |

### Драйверы (по умолчанию все OFF)


| Флаг                           | Назначение                                                                                              |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `NATALIA_ENABLE_UNICAN_DRIVER`     | Драйвер UniCAN поверх CAN1.                                                                          |
| `NATALIA_ENABLE_NAND_DRIVER`       | NAND через QSPI (научная память).                                                               |
| `NATALIA_ENABLE_MRAM_DRIVER`       | MRAM через SPI (конфигурация и служебные данные).                                |
| `NATALIA_ENABLE_SPI_DRIVER`        | SPI (нужен для MRAM).                                                                                     |
| `NATALIA_ENABLE_I2C_DRIVER`        | I2C (нужен для INA219/TMP112).                                                                            |
| `NATALIA_ENABLE_INA219_DRIVER`     | Монитор питания INA219.                                                                             |
| `NATALIA_ENABLE_ADC_DRIVER`        | ADC (нужен для TC1047).                                                                                   |
| `NATALIA_ENABLE_TC1047_DRIVER`     | Аналоговый датчик температуры TC1047.**Аппаратный дефект платы.** |
| `NATALIA_ENABLE_PED_REG_DRIVER`    | Драйвер PED_REG. ПЭД на текущем стенде отсутствует.                           |
| `NATALIA_ENABLE_USB_DEVICE_DRIVER` | USB CDC (вывод данных в DUMP).                                                                        |
| `NATALIA_ENABLE_FTDI_DRIVER`       | Вывод через FTDI/USART1.**Аппаратный дефект платы.**                               |
| `NATALIA_ENABLE_BOARD_TEST_HOOKS`  | Тестовые хуки Board_API для стендовых проверок.                                   |

### Аппаратные параметры


| Флаг                                | Назначение                                                          |
| --------------------------------------- | ----------------------------------------------------------------------------- |
| `NATALIA_NAND_POWER_SWITCH` (`FPF2101`) | Ключ питания NAND:`FPF2101` (OFF=HIGH) или `FPF2006` (OFF=LOW). |
| `NATALIA_QSPI_TARGET_HZ` (`40000000`)   | Тактовая QSPI для NAND.                                            |
| `NATALIA_QSPI_DMA_READ/WRITE` (ON)      | DMA для чтения/записи NAND.                                    |
| `NATALIA_SPI_DMA_READ/WRITE` (ON)       | DMA для чтения/записи MRAM.                                    |
| `NATALIA_SPI_MRAM_BR` (`0`)             | Делитель SPI для MRAM.                                             |

> Взаимоисключения (проверяются CMake): `FTDI` и `USB_DEVICE` делят PA9/PA11/PA12;
> `FTDI` конфликтует с `LOG_BACKEND=LPUART1` (общий PG8).

## 7. Стендовые bring-up main'ы

Для проверки отдельной периферии на плате прошивочный `main` можно заменить через
`NATALIA_FIRMWARE_MAIN`. Каждый файл в `tests/firmware/` — самостоятельная
программа проверки одного узла.

```bash
cmake -S . -B cmake-build-debug -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=Toolchain_STM32L4.cmake \
  -DNATALIA_FIRMWARE_MAIN=tests/firmware/mram_store_test.c \
  -DNATALIA_USE_BOARD_STUBS=OFF \
  -DNATALIA_ENABLE_MRAM_DRIVER=ON -DNATALIA_ENABLE_SPI_DRIVER=ON \
  -DNATALIA_LOG_BACKEND=CAN

cmake --build cmake-build-debug --target natalia_firmware -j 18
```

Ключевые проверки (не полный список):


| Файл                                 | Проверяет                                            |
| ---------------------------------------- | ------------------------------------------------------------- |
| `can_test.c`                             | CAN1 приём/передача                              |
| `mram_test.c` / `mram_full_test.c`       | MRAM чтение/запись/удержание             |
| `mram_store_test.c`                      | MRAM-store (конфиг/служебные данные/CRC) |
| `nand_full_test.c` / `nand_bench_test.c` | NAND стирание/запись/верификация     |
| `ina219_test.c`                          | Монитор питания INA219                          |
| `tmp112_test.c`                          | Датчик температуры TMP112                    |
| `dump_test.c` / `usb_*` .c               | Вывод данных по USB                              |
| `PED_and_CAN_test.c`                     | Совместная проверка CAN + PED_REG           |

Каждому main'у нужно включить соответствующие драйверы через `-D...=ON` и выбрать
подходящий `NATALIA_LOG_BACKEND` (на стенде обычно `CAN` — вывод в
Nucleo-L496 транслятор CAN→LPUART1).

## 8. Статус режимов


| Режим / команда                    | Статус                                                                                                                                                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| INIT /`EVENT_BOOT`                             | Готово: init -> проверка/восстановление/загрузка MRAM -> DUTY.                                                                                                                                                |
| DUTY                                           | Диспетчеризация готова;`SET_CFG` (0007h) проверен тестами.                                                                                                                                                    |
| SET_CFG (0007h)                                | Готово: декод 66 байт, запись обеих копий MRAM, пересчёт маски аварий.                                                                                                                          |
| TEST (0009h)                                   | Готово: запись/чтение/сравнение по блокам,`Nerr` в MRAM, счётчик теста.                                                                                                                           |
| Результаты теста (000Ah→0203h) | Готово: длинное ТС 6146 байт (данные + CRC из выбранной копии MRAM).                                                                                                                                     |
| ERASE (0008h)                                  | Готово: кооперативное стирание, счётчик стираний, аварии.                                                                                                                                         |
| DUMP (0006h)                                   | Готово: вывод по USB, ACK с числом пакетов, счётчик последнего пакета.                                                                                                                          |
| SHUTDOWN (0005h)                               | Готово: сохранение служебных данных, отключение питания.                                                                                                                                          |
| ALARM                                          | Обработчик готов и соответствует таблице переходов;**источники аварий (мониторинг температур/токов/напряжений) ещё не подключены.** |
| OBSERVE                                        | **Не финальный.** Поллеры/действия есть, но режим требует ПЭД и научных форматов.                                                                                                  |
| Телеметрия (ТС 0202h)              | **Заглушка** (`transport_send_telemetry` возвращает `UNSUPPORTED`).                                                                                                                                                             |

| SPI DMA                             | 🟢 Работает        |                                                                                                         |

| Температура ПЭД (TMP112, 0x49)      | 🟡 Не проверялся   | Нельзя проверить без ПЭД.                                                                                |

## 10. Текущие ограничения

- OBSERVE не финальный; научные форматы (Формат НИ) не реализованы.
- Источники аварий (мониторинг параметров) ещё не подключены — сам режим ALARM
  готов, но автоматически в него сейчас приводят только ошибка MRAM при старте и
  ручная инъекция в тестах.
- Телеметрия (ТС 0202h) — заглушка.
- Transport ещё зависит от внутренностей UniCAN; развязка за Board_API-сеамом
  запланирована отдельной фазой.
- Для свежего/стёртого MRAM обе копии не проходят CRC, и store поднимает аварию
  MRAM (штатной перезаписи заводского образа нет).

## 11. Правила разработки (кратко)

- Только C11, без C++.
- Без `malloc`/`free` и динамической памяти; статические буферы фиксированного размера.
- Никакого фонового многопоточного кода и RTOS-допущений.
- `Algorithm` — только через `board_api`, без прямого доступа к регистрам.
- Длительные операции — кооперативные и неблокирующие.
- Сборка держится тёплой по предупреждениям проекта; предупреждения не ослабляются молча.

## 12. Документация Board_API

Аппаратный контракт, через который `Algorithm` работает с железом, описан
отдельно: [`Board_API.md`](Board_API.md) — перечень функций по группам (система,
MRAM, NAND, ПЭД, RTC, температура, мониторы питания, вывод данных, связь),
коды возврата `BoardStatus` и правила уровня.
